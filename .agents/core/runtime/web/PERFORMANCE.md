# Web OS 显示性能优化

2026-10-25，本机 Chromium IAB，生产资源与现有严格 CSP。保留雪山与桌面材质；按用户最新要求，应用窗框、标题栏、内部导航、章节切换与来源抽屉改为实色，不挂载玻璃控制器、背景副本或光学观察器。未增加后端接口或修改归档。

下表记录去除窗口玻璃之前的第一阶段性能优化；最终实色窗口的同条件复测见下一节。

## 实测

1440×900、DPR 1，打开一个包含 18 轮摘要的真实对话，普通窗口为 1180×740，左上角 (48,64)。从右下角 (1228,804) 按住，24 次向左移动 12px，再 24 次向右移动 12px，每次输入间隔 16ms，最后松手。每轮回到同一尺寸。数值为 Chrome Performance metrics 差值及 renderer 主线程 trace，包含浏览器实际处理与工具输入开销，不能当作用户点击延迟或 FPS。

| 指标 | 优化前 | 优化后第 1 轮 | 优化后第 2 轮 | 优化后第 3 轮 |
| --- | ---: | ---: | ---: | ---: |
| 追踪时长 | 5.675s | 2.452s | 2.382s | 2.395s |
| 主线程 TaskDuration | 4.834s | 0.408s | 0.274s | 0.281s |
| ScriptDuration | 4.407s | 0.183s | 0.061s | 0.061s |
| 超过 50ms 的主线程任务 | 37 | 1 | 0 | 0 |
| 最长主线程任务 | 162.5ms | 109.5ms | 11.5ms | 11.3ms |
| LayoutCount | 338 | 175 | 174 | 175 |
| RecalcStyleCount | 658 | 333 | 332 | 333 |

优化后三轮主线程耗时中位数 0.281s，相对基线降低约 94%；首次复测为 0.408s，降低约 92%。首轮仍观察到一个长任务，不宣称消除所有卡顿。优化前桌面空闲追踪 17.38s 内仅消耗 0.117s 主线程时间，主要瓶颈发生在交互期间。

原始 trace、metrics、comparison.json 及截图保留在本机忽略目录 `.impeccable/review/web-os-performance/`，不包含在发行资源中。基线只有一轮，后续可在目标硬件重复同一动作；没有将本次结果外推为所有浏览器或所有设备的帧率保证。

主线程耗时中位数 0.218s，相对最初 4.834s 基线减少约 95.5%。记录见 `solid-resize-1/2/3.json`、对应 metrics 及 `solid-comparison.json`。

## 实现

- 参考 [ProzillaOS WindowView](https://github.com/Prozilla/ProzillaOS/blob/c94470a868054b21acf9a8bb0b39fedc9a718591/packages/core/src/components/windows/WindowView.tsx) 的窗口 memo 隔离与外层 Draggable。KSF 保留自己的窗口、材质与应用模型；没有替换为整个 OS 框架，也没有进行两项目的同条件跑分。
- 缩放期间复用已解码的折射贴图，实时更新透镜几何、裁切和背景对齐；松手后精确重建。最终版本仅桌面卡片使用该光学路径；应用窗口只更新普通布局。首次无贴图时正常生成，不出现空白玻璃。
- Surface 更新仅作用于正在移动或滚动的区域；每帧先统一读取布局，再统一写样式。阅读正文不再触发桌面、Dock 与其他窗口的玻璃测量。
- Blink/Gecko 保持滤镜 ID 稳定，WebKit 保留换 ID 和延迟重绘兼容处理。平坦中心用原生像素填充，边缘光学算法保持不变。
- 将时钟隔离到独立组件并按分钟更新。窗口、对话、归档消息与 Markdown 复用未变化的渲染结果；连续缩放时只在跨容器断点及结束时更新业务布局宽度。
- 共享请求缓存对 JSON 作结构共享，相同响应不通知订阅者；变化的时间、消息修订、错误与恢复仍会更新。完整轮次合并及消息分组按数据变化重新计算。
- 滚动位置立即进入窗口内存；本机存储和 history 合并到滚动停顿后，点击、按键和 pagehide 前刷新。最小化和显示桌面时暂停所属业务订阅，保留原有隐藏页轮询限制。

## 验证

- TypeScript、38 项前端测试、20 项相关 Web/任务/资源测试及生产、Core 构建通过。新增用例覆盖轮询无变化、失败恢复、消息结构共享，以及 6 类透镜的原始像素 SHA-256 回归。
- 第一阶段实际 SVG 检查：缩放中 feImage 保持原贴图；松手后生成新尺寸贴图；Blink filter ID 稳定。窗框模糊从 12 调至 13 时实际 stdDeviation 更新，随后已恢复 12。
- 双窗并排可独立滚动。刷新后恢复阅读定位，并按新窗口内容范围限制滚动位置。窗口与卡片移动、缩放后背景保持对齐；卡片取消恢复原布局。
- 关闭全部窗口回到 7 个桌面滤镜。生产控制台未见 error/warn 或 CSP 拒绝。桌面材质参数、用户档案原文与 PC 范围保持原约定；应用内光学参数保留为兼容数据，已从设置中移除。
- 本轮验证为当前 Agent 的 Chromium 本机走查，未开展 Safari/Firefox、低配硬件或用户设备的 FPS 验收。Vite 大于 500kB 的 JS 分块提示仍存在。

## 第二轮：打开、拖动、切换与长对话滚动

2026-10-25，继续使用实色应用窗口，1440×900、DPR 1、本机 Chromium 生产页面。普通路径和压力条件分别记录，不将自动化工具等待时间称为浏览器 INP。

| 普通路径 | 本轮优化前最长主线程任务 | 最终最长主线程任务 | 最终超过 50ms 的任务 |
| --- | ---: | ---: | ---: |
| 桌面最近对话打开应用，到第18轮正文出现 | 26.62ms | 21.62ms | 0 |
| 标题栏向右120px再返回，48次输入 | 5.79ms | 5.22ms | 0 |
| 第18轮切换到第1轮，等待新正文且结束忙碌状态 | 21.80ms | 11.41ms | 0 |
| 展开过程记录后，24次向下120px，再24次向上120px | 2.92ms | 2.94ms | 0 |

普通拖动和滚动本来没有明显长任务，本轮不宣称它们有显著提升。切换的累计主线程时间由80.97ms降到52.17ms，点击事件处理由8.68ms降到2.27ms；脚本、布局、接口读取和等待分别保留在trace中。

打开应用的最终正文就绪观察值为197.6ms；优化过程中的三轮复测为172.9–272.8ms。该值包含本地请求及自动化通信开销，受归档读取波动影响，不作为精确点击延迟或跨设备承诺。最终打开的累计主线程时间76.76ms，原基线96.78ms。已移除显式聊天打开时不需要的默认聊天请求；自动选取时与目录共用第一页。

长滚动样本为18轮对话中的第1轮：11条原始消息，展开后约5965px文档、476px阅读视口、524个正文DOM节点。相同滚动输入的中点均到2883px。另检查2789字符的长请求：首次展开入口正常，原文长度保持2789；完整展开过程记录、收起再打开和结构化问答均保留原有内容。

| --- | ---: | ---: |

可中断渲染把重工作移出了点击任务，但压力条件下仍存在约59–65ms的渲染帧峰值，未宣称完全消除卡顿或达到固定FPS。首次展开过程记录的压力复测最长29.15ms、无超过50ms任务；没有简单把全部阻塞移到展开操作。节流测试不等于真实低配硬件验收。

### 本轮调整

- 复用短日期与完整日期的格式器，保留本地时区和每条实时输入值，避免列表反复构建Intl实例。
- 收起的过程记录首次展开时再处理问答上下文与Markdown；展开后保留组件，收起和重开不丢失状态。
- 长请求使用ResizeObserver初始通知测量，取消挂载时的同步强制布局。
- 轮次选择采用React可中断更新，提供忙碌状态。手动选择保持列表位置，深链接和浏览器导航仍自动定位；修正快速点击时自动滚动与延迟更新的冲突。
- 阅读位置即时进入窗口内存，写入history前核对当前URL轮次，避免未完成切换把旧位置写给新轮次。
- 为应用根与滚动正文增加布局隔离；显式聊天跳过默认选择查询，必要时复用目录第一页。不更改服务端接口和归档格式。

- 39项前端测试、20项Web/任务/资源测试、类型检查、生产与Core构建通过。新增日期格式语义回归；既有结构化问答、附件、修订、原文与安全链接测试继续通过。
- 压力下快速点击18→2→1后，最终正文和选中项均为第1轮，忙碌状态正常结束。无显式章节的浏览器返回恢复723px；显式章节定位继续优先。

## 卡片编辑：格内像素刷新修复（2026-10-26）

用户在上一轮减少玻璃更新后仍反馈卡顿。重新隔离后，根因是react-grid-layout 2.3.0的刷新遗漏：GridItemInner在onDrag/onResize中只更新像素位置ref，而GridItem的memo只比较整数x/y/w/h等属性。格内移动没有改变这些属性，卡片因而停住，跨格才跳动；与格数多少或网格线绘制开销不同。

本机Chromium、1920×1080的实际指针检查：归属卡初始x972/y128，鼠标分别偏移10px和40px，修复前两次仍停在x972/y128；修复后分别到x982/y138和x1012/y168。尺寸初始276×276，缩放手柄偏移10px和40px后分别为286×286与316×316；松手仍按150px步长落到整数格。3×3结果426×426，完成并刷新保持；随后已恢复原2×2布局并逐项核对全部三卡坐标。

CardGrid保留原库和既有布局、碰撞、边缘滚动及键盘能力，只将活动卡片的内容元素引用按requestAnimationFrame刷新。其他卡片内容引用保留，不重建内容；连续事件每帧最多刷新一次。桌面草稿只在停止操作时更新；结束、退出编辑和卸载取消排队刷新，无新增依赖或存储字段。正方形参考格和24px间距保持。

相同120点、约2.4秒的连续拖动输入中，Trace DrawFrame计数25→121；这是该采样的绘制次数，不当作设备稳定FPS。基线另开启了CPU采样，修复后只采Trace，因此不拿两次TaskDuration作严格耗时降幅比较。确定性结论来自格内10px/40px的实际DOM坐标与尺寸检查。520×760下10px移动同样跟随，无横向溢出；取消后回宽屏，保存布局未变。

前端63项测试覆盖现有布局数据与新增活动卡片引用、事件合并和停止后旧帧清理。浏览器采样仅为本机Chromium，其他浏览器及真实低配设备另验收。原始Trace、CPU采样、DOM坐标、截图与构建日志位于项目验收目录“工作台-网格拖拽性能-2026-10-26”，不进入发行资源。
