# KSF合作 · Cooperation Center

Core 自带应用 `com.ksf.cooperation-center`（工程 `@ksf/cooperation-center`）。升级来源为固定的 `ksf-apps`，随包文件仅作为离线基线。旧内网通信应用源码已迁入此目录；独立仓库留作历史，不再发布旧身份。

合作方按 KSF 实例身份识别。相同姓名、同一人拥有的多台电脑不会共享规则或权限。配对只授予消息收发，不授予 Agent 执行权限。

每个实例发布自己的承接声明，说明能做什么、需要哪些材料和预期交付。所有已配对实例均可查看，并在发任务时选择。每项声明独立配置人工／先拟方案确认／Agent 自主处理，以及执行范围和交付方式；不再按发送实例配置规则。默认“手动处理”常驻，无需配置 Agent。声明及授权保存在本实例 runtime，由 Core AI 服务持有；目录仅同步公开字段，CLI 无法自行授权或冒充人工确认。

任务的承接与交付由 B 管理，提交成果即完成；A 后续工作使用关联请求。任务状态、送达回执、业务接管回执与 AI 执行回执分别保存。未知结果核对原操作，不盲目重做。

## 源码与运行

- `backend.mjs`：窗口和 CLI 的公共入口、旧消息导入、后台恢复。
- `lib/store.mjs`：SQLite/WAL、事务、FTS5 中文子串检索、操作回执与实例绑定。
- `lib/tasks.mjs`：任务、内容版本、讨论、子任务、交付、顺序事件和幂等。
- `lib/sync.mjs`：功能探测、长期材料、离线队列、传输对账及业务回执。
- `lib/execution.mjs`：统一 AI 服务、版本确认、持久运行编号及成果汇集。
- `legacy-messages.mjs`、`messages.tsx`：保留普通文字与附件通信。
- `frontend.tsx`：五个导航、任务列表/详情、承接声明与选择、五导航及窄窗。

资料分析和文档起草支持文本材料。不能按实际权限处理的材料转为待 B 处理。项目执行需要 Codex 原生隔离探针通过；默认在独立副本操作，原项目写回必须明确启用。执行的新增/修改文件和删除清单作为成果材料保存，交付不会自动在 A 的项目中执行。

使用 Core 随包 Node 24 运行 `--test tests/*.test.mjs`。`node build.mjs` 构建到内部离线目录；`scripts/prepare-public-source.mjs <公用源仓库>` 准备同摘要发布内容，不联网、不发布。

## 数据与迁移

用户目录保存 `cooperation.sqlite`、长期 `materials/<sha256>`、传输材料及导出文件；运行授权保存在 Core runtime AI 目录。WAL/SHM 与数据库一起交由 SQLite 管理，不在运行期间单独复制数据库文件。备份前停止应用或使用 SQLite 备份机制。

旧 `messages.json` 的 schema 1 先导入、核对 SQLite 后，通过宿主迁移服务写为 schema 3 标记，宿主保留原件。新实例同样写 schema 3 标记。旧包不得回退读取此数据。复制来的数据库默认仅查看历史，不重放旧队列或运行。

身份切换必须使用配套迁移工具 `runtime/tools/matched-switch.mjs` 的 `--migrate-ids`，先 inspect、prepare，再 apply；中断使用同一回执 recover。预演冲突时保留双方目录。不要手改安装清单、不可变应用包、原始消息、回执或操作编号。

## 承接声明升级

KSF合作 0.3.0 需要 Core 0.3.4。旧按发送实例配置的规则首次读取时备份为 runtime AI 目录的 `rules.v1.<digest>.json`，转换为未发布草稿；只有 B 在窗口核对并发布后，所有已配对实例才可选择。旧授权引用失效，已有运行按原编号核对与停止，不重做副作用。复制到其他实例的授权不能生效。

任务绑定 `offerId`、`offerRevision`，保留声明快照和处理依据。旧请求或未指定声明时进入手动处理；不存在、下架或版本变化时交 B 处理，不自动改投其他声明。规则扩权不自动执行积压任务。目录展示最后同步时间，离线缓存不表示对方仍接受该版本。

不能向尚未确认支持声明协议的旧实例发送新式任务；先刷新或升级对方，普通消息不受影响。下架不删除历史和成果。schema 2 授权文件不能由旧 Core 读取；回退前保留新文件和执行回执，不直接恢复旧自动授权或重放队列。

## 工作流与三种 Agent 执行

KSF合作 0.4.0 需要 Core 0.3.5。正常任务从右侧面板发起，选择实例和声明、填写目标/公开业务字段并上传材料；任务卡集中显示状态、等待原因、下一步与主操作，讨论、材料、过程记录在下方切换。窄窗按应用窗口宽度逐层进入。

声明可选“我来处理／交给 Agent／运行工作流”。Agent 在声明配置期间选择 API、CLI 或 Desktop；API/CLI 选择统一 AI 执行配置，Desktop 选择当前项目。每项 Desktop 任务建立独立受限会话，同一任务方案确认后接续自己的会话。原生隔离能力不可用时交 B 处理，不能自动切换执行方式。明确成果回执绑定运行和任务内容版本；自然语言表示完成、对话结束或投递成功都不直接完成任务。

工作流声明固定提供应用包摘要、流程版本、输入/成果映射。可启动 B 的新运行，也可由 A 的原运行发任务并等待完成/拒绝/取消回调，两者可组合。回调关联只保存在 A 本机；持久事件至少一次通知，应用事务去重，暂停时保存结果而不推进。交付与流程接管是独立状态。见[工作流契约](../../docs/app-development/workflows.md)及[SDK 示例](../sdk/templates/workflow-provider/README.md)。

此次数据升级把 SQLite user_version 从 1 升为 2，先用 SQLite VACUUM INTO 保存包含 WAL 内容的 v1 备份；messages 标记升为 schema 3，宿主保留旧标记。Core 承接声明授权升为 schema 3，v2 文件按摘要备份后保留原声明版本与授权。未知运行保持原编号并先对账，不因迁移自动重跑。
