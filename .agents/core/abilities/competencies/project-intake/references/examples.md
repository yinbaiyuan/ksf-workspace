# 项目接入与补全模拟案例

以下为虚构方法案例，不是历史成功或实际验收证据。

## 首次接入普通材料

用户要求把“星河客户资料”接入星河方案。先核对是否已有项目，读取需求和方案目录说明；确认普通材料默认复制、保留原件。建立必要根卡后 plan/apply，根卡仅介绍需求、方案等分区。预算未确认就保留未知。合格结果是原件不变、复制可核对、入口逐层可读；只复制成功却声称已核实所有附件不合格。

## 补齐已有项目

用户要求补全已有星河方案入口。原项目有需求正文、当前方案及工程关联，缺当前状态和分区概览。复用根卡、核对来源、补入必要概述与入口，不复制已有材料，不新建同名项目或 Git 工程。没有长期能力偏好要求时不自动填写 routing。

## 增量冲突与恢复

再次接入时旧需求的来源变了，目标副本也已手改，同时新增了一份现场说明。保留旧副本并报告差异，复制无冲突现场说明，不自动保存另一版需求或认定最新版已采用。若中断发生在文件发布后、记录写入前，下一次计划先核对已存在副本，再补齐记录并处理剩余文件，不能覆盖或重复复制。

## 工程与归属边界

材料中包含一个 `.git` 工程，不能把整个工程当普通资料复制。交回 runtime 核实实际 Git 根和项目归属后用 repository link。多个项目均成立时先澄清影响落点的选择；独立材料盘点可以先做。用户只要求查看缺口时，全程保持只读。
