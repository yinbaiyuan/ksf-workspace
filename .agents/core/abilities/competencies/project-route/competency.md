# project-route

## 独立结果与边界

形成足以继续当前任务的项目上下文：明确主项目或无项目、实际读取的事实与来源、工作区关联、未决条件和下一步。结果先保存在当前任务底稿，不自动生成持久绑定或项目文件。

本基本功由 ksf-runtime 按需使用，属于固定系统运行机制，用户区同名对象不能接管。能力选择由 ability-route 持有；本基本功只解决项目归属与事实准备，不代替协同或搭档的专业判断。

发现根卡、来源或入口缺口时，把具体缺口及影响返回 runtime。用户明确要求创建、导入、整理或补全项目时，由 runtime 按[项目接入与补全](../project-intake/competency.md)组织专业处理，再按资产维护落实保存；本路由不自行复制材料、补写事实或在每轮任务持久补全项目。

当任务需要项目背景、已有安排关联了项目、用户指定项目或需要核实工程关系时使用。独立问答、一次性操作和空库任务都可以没有项目，不为完成路由创建项目。

## 输入与读取顺序

使用当前请求、已有任务安排、已知项目根卡、实际工作区和用户给出的文件。先核实 ksf-runtime 定位的 KSF 根目录，再解析相对路径，不把业务工作区当成 KSF 根。

项目稳定入口为 KSF 根下的 `项目/<项目名>/project.md`。根卡是普通 Markdown，不要求能力对象 ID、版本或 user_revision。正文按实际需要说明目标、范围、当前事实、有效决定、成果、工程入口、来源和下一步；缺失内容保持未知。

1. 继续任务先用当前根的 `ksf project read <项目目录名> --part all --json` 复核原根卡，再沿指定任务链接读取检查点、当前产物与本轮受影响事实；仍有效时复用，不重新遍历项目。根卡有多个未完成任务而用户未明确时先澄清，不自动采用最新文件。
2. 用户明确给出根卡时优先核对它；普通项目文件先定位所属根卡，不能把资料引用直接当作主归属。CLI 的目标是指定 scope 下的单层项目目录名，不是路径或 metadata.name 显示名；current 位于 `项目/`，archived 位于固定 `档案/项目/`。
3. 需要发现候选时，调用当前根的 `ksf project list --json`，检查退出码、`data.complete`、`data.projects` 与 errors。默认只列当前项目；明确追溯、归档调阅或候选仍有必要缺口时使用 `--scope archived` 或 `--scope all`。两种位置都只发现项目直接根卡，更深层同名文件是资料，不另建归属。CLI 不跟随项目目录或根卡的符号链接，也不搜索其他知识库。
4. 先看 list 返回的路径、标题、原始 description 和 status，再用 `project read <目录名> --part metadata|body|all --json` 读取区分候选所需内容；沿实际返回的 scope 和 path 读取、check，不把档案项目误定位到当前目录。同名跨 scope 时明确区分，不能凭显示名称合并。缺少元数据是正常状态，损坏或不可读需要单独报告。read 不展开资料，必要章节和领域入口仍按需下钻。
5. 已明确退出活跃使用的项目不进入默认选择；list 不自动隐藏它们，由 Agent 判断是否适用。complete 为 true 的空集合表示无候选，目录缺失或部分失败是读取缺口；不能把命令无输出或残缺集合当作完整空库。

上述 `ksf` 使用已核实根下的 `.agents/ksf`，跨工作区使用入口绝对路径。命令行为见 [project CLI](../../../docs/cli/project.md)。出现调用错误先查 `project --help`；执行失败保留有效部分与具体缺口，不自行换根或补建项目。必要时用宿主文件工具核对已知根卡，但不因此宣称已完成全量发现。

发现缺口只阻止依赖缺失事实的判断。用户已经给出充分材料、任务可独立完成时，继续处理，不伪称完成了全库项目排除。

## 项目预设与能力安排交接

协同过程、返回内容和完整分支遵循[核心运行、项目与能力路由协作](../../../docs/runtime/routing.md)。本基本功只向 runtime 返回，不自行调用能力路由。把主项目、资料范围、工程状态、原始 routing、逐项校验结果及具体缺口交给它；后续补充只读受影响事实。

根卡可选 routing 含 cooperations、partners、competencies、data_packages 列表，结构以[项目 CLI](../../../docs/cli/project.md)为准，示例见[配置模板](../../../docs/templates/project-routing.md)。读取根卡后：没有 routing 则明确无预设；存在时执行 `ksf project check <项目目录名> --json`，读取 data.routing.entries 和 errors，把有效项和错误一起返回。check 失败不阻止 project read 取得其他事实，不将失效配置当作无项目。

能力项提供精确 ref 和可选 source；显式来源仅约束该项。这里不按配置直接执行、不加载全部能力或资料正文、不替对象读个人设置。项目偏好由能力路由核对任务适用性，资料由承接能力按明确约定采用。配置不授予写入权，也不充当强制入口或候选白名单。

预设缺失、归档、版本不符、来源歧义，返回具体项、影响和可用部分，保留原配置，不自动换版本或补文件。Core 更新后重新采用时复核，不将项目偏好新增为升级硬依赖。硬约束与当前项目决定通过实际已确认正文及来源准备，不能从 routing 偏好推导。

项目事实沿根卡、指定检查点、实际工程及其事实来源准备，可在能力选择前取得理解目标所必需的事实。根卡里的方法论链接只是引用，不能自动作为补充方法入口；方法需要由能力安排确定。旧位置中的项目事实仍可按明确来源核对，不按物理目录一刀切禁读，也不沿事实来源扩大到知识方法检索。

`routing.knowledge` 已移除。旧根卡可 read/list，check 返回 PROJECT_ROUTING_KNOWLEDGE_REMOVED 和清理指引，保留其他可用项及项目事实，不检查旧目标路径；不自动删除该字段或改写真实项目。

## 归属判断

| 情况 | 处理 |
| --- | --- |
| 原主项目仍有效，本轮只是追问、补材料或局部纠错 | 保留主归属，只补受影响事实 |
| 用户明确指定项目且正文与目标相符 | 采用该项目，说明必要的事实缺口 |
| 项目目标、当前事项和已核实工程关系共同指向一个候选 | 读取根卡相关正文后确定主归属，保留判断来源 |
| 多个候选都成立，选择会改变资料或写入位置 | 给出具体候选与推荐，澄清后再进行依赖归属的动作 |
| 只有项目名称相似、cwd 相同或引用了项目资料 | 仅作为线索，不据此绑定 |
| 无候选且本次工作不需要长期项目 | 按无项目继续，不自动创建根卡 |
| 用户明确更换项目或目标 | 保留有效产物与授权，重审受影响归属，并交回 runtime 按需使用 ability-route 核对能力安排 |

无项目是正常结果，不需要知识或能力先找到项目才能工作。指定项目不存在应明确报告；只有明确要求创建才交资产维护落实。档案 scope 或原位 status 为 archived 的项目默认不选，明确指定可按请求读取，不自动恢复或改 active。发现失败或根卡损坏不能当作无项目。归属未定但已授权文件可独立处理时，保留待定状态继续指定范围内工作。

一个任务确定一个主项目；其他项目作为明确范围的资料引用。多个独立交付需要分别处理时，在本次任务底稿分别说明，不自动创建跨项目协同。归属确定不产生写入权，实际写入仍以任务授权为准。

## 项目事实与工程事实

先读取根卡中的目标、当前状态、有效决定和本次命中章节；有领域入口时只沿相关链接下钻，不批量读取项目目录。根卡摘要不能替代重要事实的原文。根卡与资料冲突时核对来源、时间和用户决定，无法消除的冲突交给用户。

工程关联优先读取根卡可选元数据 `repositories`（路径字符串列表），通过当前根的 `ksf repository list --project <项目目录名> --json` 或 `check --project <项目目录名> --json` 核实。档案项目在对应命令显式传入 `--scope archived`；保存的相对路径以实际根卡所在目录解析，外部绝对路径只在当前宿主核实。旧项目正文中的工作区链接仍可按需使用，不自动转换或迁移；若与结构化关联冲突，先查明当前有效入口。

新工程默认放在当前 KSF 用户根的 `repositories/<工程名>/`，名称不加 KSF 前缀；该容器由外层 KSF Git 忽略，工程各自管理 Git。一个项目可以关联多个工程，同一工程也可供多个项目使用；不要求名称相同或一一对应。仅有目标、讨论或一次性问答时不创建工程；已要求产出实际代码、文档或成果且没有可用工作区时，形成具体创建与关联安排，交回 runtime 按资产维护落实。已有工程原位关联，不为接入复制代码或强制集中。`repositories/` 首次需要时建立，不是启动必需目录，也不进入能力发现集合。

目录移动或 worktree 变化时重新检查，不把旧路径当作永久身份。需要进入 Git 工程时，在工程工作目录执行 `git rev-parse --show-toplevel`，确认返回的真实根正是选定工程，而不是继承了父 KSF 仓库，再读取实际 `AGENTS.md`、工程说明和必要源码，检查 Git 状态。repository CLI 可核实无初始提交的普通仓库和已有 Git worktree；非 Git 工作区保持其真实状态，不在关联时静默初始化。

项目保存业务目标、决定与稳定进展；代码、工程文档、构建和测试事实以实际工程为源。已有工程原位关联，不为接入复制代码或逐仓改写入口。工程规则约束工程操作，项目上下文不覆盖工程权限和宿主规则。

跨工程操作分别核对目标和改动基线；私人知识不复制到共享工程。工程结果未知时先对账。项目事实的写回由资产维护处理，不能因为读取了工程就自动更新根卡、移动文件或提交 Git。

项目从建立、活跃推进到完成或中止后收口，已归档项目退出默认活跃选择。项目归档与恢复由资产维护按档案根说明预览、移动项目记录并检查入口；移除根卡或解除关联同样保留工程原位及其 Git 历史；物理移动或删除工程必须作为明确的独立任务处理。关联失效时报告具体路径，继续不依赖该工程的部分，不在同名新目录重建以掩盖缺口。

## 交付与检查

交回 ksf-runtime：主项目及根卡，或无项目/归属待定/读取失败；routing 原始偏好、逐项有效结果；采用依据；实际读取的事实与文件；已核实工作区与工程规则入口；未决问题及可继续的下一步。只展示影响用户判断的信息，不强制输出内部字段表。

检查：继续任务没有无故重启；主归属与资料引用分开；重要事实有原文；没有凭目录授予写入权；读取失败没有冒充无项目。新会话按[任务检查点约定](../../../docs/runtime/task-checkpoints.md)沿根卡读取 `任务/<任务名>.md`，将目标、当前步骤、采用定义和授权等事实交回 runtime 复核；不批量展开全部任务文件，不把已完成或取消记录当成待办。未保存的任务安排不能声称自动恢复，工程路径或产物变化保持未知直至实际核实。

## 情境与验证

- 空库、简单问答：按无项目继续，不创建根卡。
- “继续上一版报价”：复核原项目和本次修改所需事实，不重新全库匹配。
- 两个项目关联同一工程：保留两个候选，目标仍不明确时先澄清。
- 引用另一个项目的案例：主归属不变，只读取授权范围内的相关材料。
- 工作区与根卡不一致、路径不可读：报告具体缺口，继续不依赖该入口的工作。

以上是待验证场景，实际读取、选择和结果分别记录。文件存在或结构检查成功不证明归属正确；程序检查、Agent 走查和真实任务证据分开。

本文 CLI 示例采用 macOS 的 `.agents/ksf`；Windows 入口为 `.agents/ksf.ps1`，现已接入随包运行时与共享业务 CLI；Windows 调用使用 powershell.exe -NoProfile -ExecutionPolicy Bypass -File .agents/ksf.ps1。入口恢复不等于对象发现或读取成功；受限时继续不依赖 CLI 的工作，不用全局 Node 绕过。支持边界见[启动入口](../../../runtime/launcher.md)。
