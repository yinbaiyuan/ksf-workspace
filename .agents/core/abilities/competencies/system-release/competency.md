# 系统发行

## 结果与输入

输入为用户的构建、正式发布或模板恢复要求，所在 KSF 根，远程 Core 的版本、精确源码提交、平台和有效授权；本地构建另外需要纯系统 Core 根与输出目录。结果是可检查的本地产物，或分别核对过的 Core Release 与官方 workspace 模板。实例只是操作入口，不因此成为正式源码或获得官方发布权限。

## 方法与失败处理

1. 读取[Git 规则](../../../docs/git.md)，区分当前用户实例和 Core 源。发布只取已进入远程 Core 的提交；本地未提交、尚未贡献或尚未合并的修改不进入发行。版本来自 Core 版本配置，不自动递增、不手填发行凭据。核对远程版本、准确提交、既有同版本 tag 和 Release；同版本不同来源不能覆盖。
2. **用户实例可以发起远程发布，无需维护本地 Core 克隆。** 核对官方 Core 的实际 Actions 定义已支持当前流程、发起账户有运行权限、App 配置就绪，再展示本次版本、来源和两个发布目标。只有用户明确要求正式发布才触发；用户只讨论、实现或验证时不触发。向指定官方仓库发起 Actions，不从实例 origin 猜测目标；GitHub App 的模板写权限不能代替发起者的 Core 权限。
3. 正常发布选择 `operation=release`；模板恢复选择 `operation=template-only` 并指定准确 `release_tag`。具体 gh 命令、输入和阶段协议见[发行说明](../../../docs/distribution.md#从用户实例发起远程发行)。发起一次后记录请求时间、Core 提交及返回的运行标识，再查询实际运行；无返回标识时按工作流、事件、发起者、提交和时间核对，候选不唯一或请求结果未知时保留现场，不直接重发或把最新运行当成本次运行。
4. 跟踪准备、Core 发布和模板同步三个阶段。后续阶段复用同一 artifact ID、索引摘要和 Core 来源，不重新构建或查询 latest。Core 成功但模板失败属于部分成功，只重跑失败作业；产物过期后按原发布标签恢复模板。未知响应先核对实际远程状态，既有正式资产不可替换，不为重试删除远程产物。模板版本倒退、同版本换源、分支竞争或校验失败时停止写入并交回实际状态。
5. **本地 Core 构建分支。** 核实干净纯系统提交与随包平台，运行 `runtime verify`、`test` 及 `release build`，再核对产物、版本、来源和摘要，隔离验证首次启动。试验性的 `--allow-dirty` 产物只能是 development 包，不能作为正式发行。仅要求构建时到此交付。本地授权发布先 `release publish <目录> --dry-run --json`，再执行实际命令；`--release-only` 仅表示未执行模板，不承诺已安排后续任务。
6. 正式发行后复核 Release 标签、资产和实际公开状态；模板核对实际分支、提交、来源标识及发行凭据。成功返回必须有程序对账证据。向 runtime 交回两个独立结果、版本和准确 Core 提交、链接、未决项及原任务恢复点。

## 验收与边界

本地构建、模拟 API、真实 App 访问、正式远程发布与 Agent 行为走查分别记录。App 令牌范围验证和读取成功不证明模板写入已实测；构建成功不等于正式发行。凭证按工具契约取得，不进入产物、日志或实例配置。

正例：从用户实例发起已合并 Core 版本的远程发行；Core 成功、模板失败后用同一包独立恢复。反例：打包用户实例作为官方源码、把未合并修改称为已发布、仅凭缓存或运行成功徽标声称两个目标均已更新。边界例：远程模板已是更高版本时拒绝旧任务覆盖。

当前实际平台为 macOS ARM64，Windows 启动器检查不代表完整平台支持。技术协议和配置只由[发行说明](../../../docs/distribution.md)与[release CLI](../../../docs/cli/release.md)持有。
