# 工作流设计

## 独立结果与适用边界

产出能够组织多个搭档共同完成一类业务任务的工作流定义，包括适用范围、整体结果、参与责任、协作结构、交接及整体完成条件。

普通工作流以多个独立搭档之间存在可复用协同需求为成立条件。步骤多、工作量大或工具多不单独构成理由；单个搭档的内部过程由搭档及所用基本功承载。发现无需独立工作流时，给出承载建议就是有效结果，不强行生成。

根 [AGENTS.md](../../../../../AGENTS.md) 是已有的特殊入口工作流；只有任务明确涉及它时才按其特殊契约设计，不用此例外放宽普通工作流的边界。

## 必要输入

需要明确整体业务目标、典型任务、输入和结果、参与责任、现有搭档、关键约束以及当前交接问题。先读目标定义和相关对象，再补会改变分工或交接的缺口。

参与者尚不明确时先提出责任分工建议，再判断由已有搭档承接还是需要新建。不存在的搭档只作待建设依赖；用户要求完整交付时继续补齐所需定义，不能把名字列在表里就算可执行。

## 设计方法

### 1. 判断协同必要性

检查是否至少存在两个有独立结果的责任，是否需要交接、协调或共同验收，以及这种安排是否值得复用。比较沿用现有流程、完善现有流程和新建的必要性，避免重复协调对象。

### 2. 从整体结果反推责任

先定义成功结果及验收，再划分谁提供哪些成果、谁负责整体协调和收口。每个成果和重要决定有明确责任方；用户参与点也是协同的一部分，但用户不必被建成搭档对象。

不把一个完整专业责任人为拆成多个搭档。工作流描述谁负责、何时接手和怎样验收；如何专业处理由搭档引用的基本功负责。

### 3. 建立阶段和依赖

按实际依赖选择顺序、条件分支、可选模块、反馈循环或并行安排。并行只在输入充分、责任独立且不会竞争同一可写成果时采用；实际是否使用多个 Agent 由宿主能力、用户授权及执行安排决定，不能由定义假定已经发生。

每个阶段说明：目标、责任搭档、前置条件、输入引用、产物、阶段完成条件、下一去向。无必要不增加独立阶段或确认关卡。

### 4. 定义交接契约

每次关键交接至少说明：

- 交什么成果、按哪个当前版本或位置读取。
- 保留哪些事实、来源、假设、限制和未决项。
- 接收方用什么条件判断可接手。
- 信息缺失或不合格时返回谁、补什么。
- 接收后谁继续维护该成果，避免多方覆盖或重复正文。

交接完整性由工作流检查；成果的专业质量引用相应责任方与基本功标准，不在工作流复制另一套标准。

### 5. 定义协调和变化处理

明确分歧由谁整理依据、谁提出推荐、谁裁决哪些取舍。新信息改变上游结果时，识别受影响的下游成果，重新校验或返工；未受影响部分继续保留。

输入不足可返回补充，支持不可用可采用真实可行的替代方案，不能悄悄更改验收标准。用户变更目标时重算范围和依赖；暂停时记录进度与恢复位置；提前结束时交付已完成部分并说明剩余依赖。

### 6. 定义整体验收

整体完成至少要求：所有本次必需成果达标、交接问题已处理、跨成果一致、关键未决项按约定解决或明确保留。某一搭档完成不代表整体完成；格式齐全不代表业务目标达成。

流程只有当前任务安排时不要自动保存为长期工作流。长期定义应保留可复用规则，具体人员、文件版本、执行进度和临时判断保留在任务记录。

## 最小定义结构

沿用[对象元数据规范](../../../docs/对象元数据规范.md)。正文覆盖：

1. 适用场景、不适用条件及整体目标。
2. 输入要求、整体成果与完成标准。
3. 参与搭档、独立职责、协调与决策分工。
4. 阶段、依赖、分支和可选模块。
5. 交接内容、接手条件和成果维护归属。
6. 分歧、返工、目标变化、暂停和恢复。
7. 已有支持、缺失依赖与验证方式。

结构按任务复杂度调整；不强制每个工作流都包含并行、循环或工具。

## 质量标准与失败信号

| 检查 | 合格标准 | 失败信号 |
| --- | --- | --- |
| 必要性 | 真有跨搭档协同需要 | 一个搭档的步骤被包装成工作流 |
| 分工 | 各有独立结果，整体有人协调 | 多人都负责同一结果却无维护归属 |
| 依赖 | 能确定当前可开始和必须等待的工作 | 阶段有名称，输入依赖不清 |
| 交接 | 接收方知道依据什么继续及如何退回 | 只有“交给下一位”，没有成果和条件 |
| 规则归属 | 协同规则与专业规则分开 | 工作流复制或覆盖专业方法 |
| 恢复 | 改变上游能追踪下游影响 | 只改源头却继续使用失效成果 |
| 完成 | 整体结果按标准验收 | 所有节点结束就自动宣称成功 |

## 正反例与验证

正例：产品设计搭档提交需求与验收条件，软件开发搭档据此实现，质量验证搭档对照条件验证；失败回到相应责任方，整体协调者处理范围取舍。它成立于责任和交接，而非一定存在三个独立 Agent。

反例：同一资料整理搭档执行读取、分类、改写、检查四步，仅为这些步骤建立四个搭档和一个工作流，增加了没有独立价值的协同。

边界例：用户明确修改特殊入口工作流时保留固定入口链约束；普通业务流程不得借用入口例外成为任意单搭档流程的存储位置。

验证至少覆盖一条端到端主路径、一次交接失败、一次上游变更及一次继续任务。记录实际输入、交付、接收判断、返工与最终结果；纸面走查与真实运行分开。没有必要创建工作流的场景同样应验证承载判断。

## 支持关系

当前以 Agent 的读取、分析和编辑能力执行本方法，不依赖新增编排程序。若使用现有检查工具，先核实其覆盖范围；程序检查通过不能证明分工合理或业务目标完成。
