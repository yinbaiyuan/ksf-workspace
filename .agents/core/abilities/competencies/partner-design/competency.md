# 搭档设计

## 独立结果与适用边界

产出能在目标情境中承接任务的搭档定义，并明确所需基本功、支持依赖和验证依据。系统搭档、用户搭档及对象设计师自身均属于设计范围。

适用于新建独立责任角色，或已有搭档出现职责不清、协作卡顿、能力配置不全、交付不稳定等问题。只增加一种专业做法时优先完善或配置基本功；只有多个搭档之间需要协同时才转入协同设计。

搭档持有职责与责任—基本功配置，基本功持有专业方法与判断标准。定义或读取搭档不会创建独立 Agent，也不授予工具和执行权限。

## 必要输入与不足处理

需要了解服务对象、使用情境、目标结果、已有搭档与能力、用户希望的参与方式以及至少一个典型任务。有现行定义时先读原文和相关引用。

缺少关键信息时提出具体候选帮助用户判断。普通表达和结构可作合理默认并说明；会改变职责、取舍或执行范围的信息必须澄清。没有真实案例时可以先用明确标记的模拟案例形成候选，但不能宣称实际有效。

## 设计方法

### 1. 写出责任和结果

用“为谁，在什么情境，持续承担什么责任，产生什么结果”表达使命。将“专业、聪明、顶级”等形容转换为可观察的动作和质量要求。

检查是否与已有搭档重叠。一个新增搭档应有可解释的独立责任；材料多、提示词长或使用新工具都不足以单独成立。

### 2. 确定主要工作类型

以下六类用于辅助设计，不是必须增加的元数据枚举，也不是整个 KSF 的固定能力分类。按主要验收结果选一个主类型，确有需要再定义辅助模式。

| 类型 | 应额外定义的信息 | 验收重点 |
| --- | --- | --- |
| 成果制作 | 原料、读者与用途、加工权限、成品规格、修改规则 | 成品是否准确、保真并可用 |
| 分析决策 | 判断问题、目标约束、候选方案、事实假设、关键变量、验证行动 | 判断是否有依据，条件和取舍是否清楚 |
| 调研建模 | 研究范围、来源计划、证据规则、比较建模方法、反例、停止条件 | 结论能否回到证据，模型边界是否明确 |
| 经验萃取 | 经历与案例、采集结构、关键判断、来源标记、迁移条件 | 忠实还原经验，推断没有冒充事实或普遍规律 |
| 知识教学 | 学习目标、前置知识、理解诊断、教学策略、纠偏与迁移检查 | 有何证据支持理解；讲过不等于掌握 |
| 技能训练 | 目标动作、评价标准、基线、题目难度、反馈、重复与进步证据 | 用户是否实际练习，表现是否改善 |

类型名称不决定行为。训练方案设计主要交付计划；只有发生实际作答、反馈和再练时才构成训练循环。模式切换必须说明触发、当前产物和返回位置，不能把辅助能力扩成无边界服务。

### 3. 定义责任、能力和判断权

将使命拆成足以覆盖结果且不重复的责任，为每项需专业处理的责任关联已有基本功。缺少基本功时标明缺口，按任务授权设计或提出支持方案；不能只写名称假装已经可用。

保留搭档自身的任务理解、能力选择、协作推进和整体收口职责。能跨搭档复用的专业规则放入基本功；用户事实和资料放在相应上下文或数据中。

分别写清能否提出判断、推荐方案、执行修改，以及由谁决定关键取舍。不要一律禁止建议，也不要把协作邀请当作执行授权。

### 4. 设计可组合的工作过程

| 流程形态 | 结构 | 需要定义 |
| --- | --- | --- |
| 一次交付 | 输入—处理—检查—交付 | 输入充分条件、加工和验收 |
| 阶段推进 | 前序成果支持后续阶段 | 阶段产物、依赖和推进条件 |
| 诊断分流 | 判断现状后选择路径 | 诊断依据、分支、未知及重诊条件 |
| 模块组合 | 按目标选择相对独立模块 | 必选/可选、依赖、共享信息、汇总 |
| 反馈迭代 | 初版/表现—评价—修改/再练 | 评价标准、变化记录、停止或升级条件 |

选择能完成目标的必要结构，允许组合，不把五种形态全部套上。发散收敛、取证推导等属于阶段内的专业方法。上述内部过程不是跨搭档 Cooperation 对象。

每个实质阶段写出目标、输入、处理动作、产物、完成条件及缺失/纠错处理。信息足够且已授权时自动推进；只有会改变结果的事实、重要取舍和权限边界才需要用户参与。禁止用固定轮数代替充分度。

### 5. 设计工作底稿和交互

多轮任务明确持续维护什么，如公式树、设计稿、证据表或训练记录。记录必要的来源、假设、用户确认、当前进度和未决项；用户纠错时更新受影响部分。

定义提问目的、回答负担、反馈方式、默认输出颗粒度及提前结束的交付。优先让用户判断具体方案，不要求用户从空白定义专业结构。单次任务不强制建立复杂状态对象。

### 6. 设计持久设置与必要状态

每次设计检查是否有需跨任务保留的协作偏好或必要状态，按[对象 user-data 设计与使用](../../partners/ksf-object-designer/references/user-data-design.md)判断归属并使用其中的可裁剪模板。无需求时记录判断，不增加空字段、固定章节或默认文件。

搭档自己消费的输出语言、详略等偏好可以成为候选字段，但示例不等于当前用户事实。给每个实际需要的字段定义类型、默认和无效处理，说明它怎样影响本搭档的提问、组织、交付或恢复行为；不只列一张设置表而不接入工作过程。基本功独立消费的专业选项归基本功持有，不能假定会继承搭档设置。

上一步的公式树、证据表、训练记录、当前进度和未决项属于工作底稿，按项目或任务约定保存。必要状态必须能解释跨任务保留的用途，且不承载这些正文、日志或成果。明确实际采用和恢复时读取、临时覆盖不回写、用户授权后的保存与清除；设计本身不授权初始化个人设置或自动学习偏好。

### 7. 配置知识、工具和交付

知识资料说明来源、版本或时效、适用阶段、调用目的和缺失处理。资料可供参考不等于结论已证实；要求检索不等于实际检索过。

工具说明实际可用能力、调用条件、权限及失败处理。只声明当前所需支持，不虚构自动保存、跨会话记忆、独立 Agent 或未实现 CLI。

定义交付内容、完成标准、未完成部分的呈现及后续修改入口。简单任务不强制生成长报告。

## 候选定义的最小信息

依据[对象元数据规范](../../../docs/对象元数据规范.md)保留元数据。正文应覆盖使命与场景、适用边界、目标与成功标准、输入与缺失处理、职责与能力配置、协作过程、工作记录、支持依赖、交付与异常处理。有持久数据需求时补齐字段、消费行为及读写维护约定。组织顺序可以调整，不要求每项独立成章。

对象版本与状态遵循公共元数据规范；用户派生保留来源版本，以 user_revision 记录修订。设计质量、验证范围和已知限制仍用正文或任务证据说明，不以 active 代替质量证据。

## 质量标准与失败信号

| 检查 | 合格标准 | 失败信号 |
| --- | --- | --- |
| 定位 | 能解释为何需要这个责任及何时使用 | 只换角色名称或笼统“全能助手” |
| 能力 | 责任有实际方法支持或明确可行的处理 | 引用空骨架却声称能力完整 |
| 归属 | 专业标准与协作规则各有唯一正文 | 搭档复制整份基本功或另写冲突标准 |
| 推进 | 能从典型输入走到可检查结果 | 只有任务清单，没有推进和结束条件 |
| 交互 | 用户参与解决真实缺口 | 每步确认、重复提问或让用户替 AI 完成设计 |
| 可信度 | 区分用户事实、资料和推断 | 把模板示例当作当前用户事实 |
| 持久数据 | 已检查需求，偏好作用明确，工作底稿保持原归属 | 只列字段不采用、把工作记录塞进设置，或擅自保存临时偏好 |
| 边界 | 能处理纠错、切换、缺失与提前结束 | 一偏离标准流程就重启或卡住 |
| 验收 | 完成声明有具体证据 | 只凭文件齐全或自评宣布有效 |

## 正反例与验证

正例：面向复盘材料整理的搭档，明确读者与用途，引用信息整理能力，先形成可用笔记，再按需重构；信息充分直接执行。反例：只写“顶级知识管理专家”，既无加工边界，也无质量标准。

边界例：同一搭档新增一种取证方法，优先补基本功；若新增的是独立学习教学责任，则评估辅助模式或另建搭档，而不是只加一个工具名。

使用典型任务检查完整链路，再检查信息不足、用户纠错、目标改变、支持不可用、提前收束和模式切换。记录输入、实际输出/行动、是否达到标准、问题及修复；预期结果不是测试结果。真实使用和独立测试分别说明，单个案例不证明全部模式已稳定。

有持久数据时按共享方法验证默认、保存后实际采用、临时覆盖、清除和错误保留，观察提问或交付确实按约定变化；无需求时核对没有创建多余记录。仅证明文件可读不能宣称跨会话协作效果已验证。

## 自举与支持

设计自身相关搭档时沿用相同标准，区分现行依据与本轮候选；结构通过不能自动使候选生效。当前方法可由 Agent 读取文件、分析、编辑和检查完成。需使用工具、脚本或 CLI 时，按基本功的方法核实适用范围、实际调用说明与结果。

## 资料读取验收

按[对象核心描述规范的资料约定](../../partners/ksf-object-designer/references/object-core.md#资料采用约定)核对用途、入口或限定范围、读取条件和缺失处理。资料由本对象或其配置能力按职责采用；不依赖独立知识路由补专业方法，不新增公共元数据，不为结构完整创建数据包。
