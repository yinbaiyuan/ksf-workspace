# 基本功设计

## 独立结果与适用边界

产出能指导一类专业处理或具体执行操作的基本功定义：知道何时使用、需要什么、怎样做判断和行动、如何检查结果，以及失败时如何修正。基本功既可以侧重专业判断，也可以侧重稳定操作，均应具有独立结果和检查标准。

适用于新增专业方法，或已有方法过于抽象、标准不清、不可操作、边界重叠或支持关系不明。系统基本功、用户基本功及本基本功自身均在范围内。

只提供事实材料时优先知识或数据包；专业方法与可复用的稳定操作统一由基本功承载，确定性实现可直接引用脚本、CLI 等支持资源；管理一类业务责任属于搭档；跨搭档协调属于工作流。是否多轮、是否用工具、篇幅长短都不是划分依据。

## 必要输入

需要明确专业问题、使用情境、预期独立结果、已有做法与依据、好坏结果差异、相关能力及支持条件。优先从真实任务、案例、原始方法和用户反馈中取证，不凭能力名称编造专家标准。

信息不足时先判断缺口是否影响方法成立。可以形成明确标记的待验证方法和模拟案例，但不能编造历史成功、用户确认或实际测试。关键标准无依据时，提出可观察的候选标准与验证方式供共建。

## 设计方法

### 1. 找到独立结果和合适粒度

用“在什么条件下，把什么输入处理成什么可检查结果”描述能力。

检查三个问题：是否能独立解释产物；是否具有一组连贯的方法和质量标准；能否被不同搭档或情境复用。拆分后只剩无独立价值的机械动作时合并；多个结果需要明显不同的专业标准、支持条件或独立调用时考虑拆分。

先比较现有基本功。新增一种步骤、工具或案例不必新建基本功；方法发生差异但结果和边界一致时，可在现有定义中增加条件分支。

### 2. 明确输入、输出和适用边界

区分必需输入、可选上下文及可以安全采用的默认条件；说明缺信息时补问、暂用假设、降级还是停止依赖该信息的判断。

输出要能被调用方继续使用，包含必要依据、置信限制和未决项。说明什么情境不适用、与相邻基本功如何分工，以及使用前是否有必要前置能力。

### 3. 把专业方法写成可执行判断

方法至少说明：

- 观察什么证据或特征。
- 用什么概念、维度、关系或标准判断。
- 不同判断分别触发什么动作。
- 产生什么中间结果和最终结果。
- 何时继续、回退、换方法或停止。

关键判断尽量写成“当出现 X、依据 Y 判断为 Z 时，采取 A；若证据不足则 B”，同时说明适用条件。对开放性专业问题保留解释和权衡空间，不用虚构分数、阈值或确定公式掩盖不确定性。

基本功可以包含专业追问、分析、操作和检查步骤；只约束完成专业处理所必要的互动，不接管搭档的整体沟通、任务路由和跨责任协作。

### 4. 写清标准、失败信号和修正

为独立结果定义可观察的质量要求，并给出常见失败及处理。将“深入、全面、高质量”改写为能检查的条件，例如关键结论有来源、比较对象口径一致、重要替代解释被考虑。

区分必须满足的要求和可优化项。标准来自已有依据时注明来源；本轮提出的标准标记为候选，不能自动获得已验证方法的地位。

### 5. 配置案例和支持资源

案例至少说明输入情境、采用的方法、结果好坏及原因、适用边界。正例展示如何达到标准，反例展示为什么失败，边界例帮助判断何时不用或需要换方法。模拟案例必须显式标注，不伪装成真实实践。

资料、数据包、模板、脚本或 CLI 按必要性引用：说明用途、调用条件、输入输出、实际可用性和缺失处理。引用名称不证明已经加载或执行。资料更新可能改变判断时说明时效检查；用户事实仍需回到当前任务来源。可独立复用的支持逻辑可以作为共享程序或资源维护，不额外建立另一类执行能力对象。

不要求每项基本功都具有程序和数据包；不为结构完整创建空支持对象。基本功持有正向支持关系，不维护使用它的搭档反向清单。对象依赖使用 references 声明，普通程序与资源的使用方式和路径由正文说明，不伪造对象 ID。

### 6. 设计方法所需的持久数据

每次设计检查专业处理是否需要跨任务保留的选项或必要状态，按[对象 user-data 设计与使用](../../partners/ksf-object-designer/references/user-data-design.md)判断并按需使用其中模板。单次输入、计算中间值、业务成果和本机缓存保留原位置；无持久需求时不增加字段、固定章节或数据文件。

每个字段说明类型、用途、默认和无效处理，并指向它实际改变的方法步骤、判断分支或输出要求。必要状态说明由什么可核实结果产生、在哪种用户授权下更新，以及恢复时如何核对；仅有一个保存命令不足以构成可用方法。基本功按自身 ID 读取，不依赖调用搭档隐式传入其私人设置；需要本次参数时在输入契约中显式传递。

写清采用和恢复时读取、临时覆盖不回写、授权后的更新和清除。定义字段语义不等于注册了程序 schema；存储通过后仍要检查类型和适用性，不能让保存值替代专业判断、工具权限或操作授权。

### 7. 用任务验证并修订

选择能暴露方法有效性和边界的案例，先写预期标准，再观察处理过程和结果。检查方法是否改变了实际判断，输出是否满足标准，失败来自方法、输入、支持条件还是执行偏差。

修订要指向失败原因，不为一个局部症状叠加冲突规则。修复后复核失败场景及受影响的相邻场景，避免只验证最容易通过的正常输入。

## 最小定义结构

按[对象元数据规范](../../../docs/对象元数据规范.md)定义元数据。正文覆盖：

1. 独立结果、使用条件与不适用边界。
2. 必需输入、可选输入与缺失处理。
3. 专业概念、方法、判断依据和动作分支。
4. 输出要求、质量标准、失败信号与修正。
5. 正例、反例、边界例及其来源性质。
6. 所需资料、数据包、脚本或 CLI 的引用和调用条件。
7. 验证方式、已有证据及尚未证明的部分。
8. 有需求时，持久字段、方法中的消费位置、授权维护及清除和异常处理。

可以合并章节，但不能以目录完整代替实质方法。不得引入未经确认的新对象版本或状态制度。

## 质量标准与失败信号

| 检查 | 合格标准 | 失败信号 |
| --- | --- | --- |
| 独立性 | 有可解释、可检查的专业结果 | 只是“负责学习”“善于思考”等泛化描述 |
| 粒度 | 方法与结果连贯，有实际复用价值 | 小到单个无意义动作，或大到所有工作都能装入 |
| 可操作 | 证据、判断、动作和产物相连 | 只列理论名称、口号或章节 |
| 可信度 | 方法来源、推断和验证状态区分清楚 | AI 生成内容冒充用户经验或稳定规律 |
| 质量 | 能检查好坏、解释失败并修正 | 只说“确保正确全面” |
| 支持 | 依赖实际存在，缺失有可行处理 | 假设有知识库、数据包或程序即可执行 |
| 归属 | 专业标准只维护在本能力正文或其明确引用源 | 复制搭档职责或维护反向关系表 |
| 持久数据 | 已检查需求，字段与实际方法和更新依据相连 | 只保存不使用、盲信旧值，或自动写入任务正文 |
| 验证 | 结论与实际证据范围一致 | 单例通过即宣称普适有效 |

## 正反例与边界例

以下为设计说明用模拟案例，不是已完成实践。

**正例：报价口径校验。** 输入为报价明细与交付要求，输出为可追溯的差异清单。方法分别核对数量、计价单位、税费、服务范围和有效期；口径缺失先标记再补问；验收看每项差异是否有来源和处理建议。它可由售前、采购等不同搭档使用。

**反例：商业高手。** 同时包揽战略、写作、销售、财务却没有独立结果、明确边界或共同方法，无法作为一项基本功检验。

**边界例：导出一个文件。** 若导出操作具有独立复用价值，可以由基本功定义输入、操作与结果检查，并直接调用现有程序；若只是另一项处理中的单步操作，保留为该基本功的一步，不强行独立建对象。该导出什么、怎样脱敏、怎样保持内容保真等判断，也由相应基本功持有，不按判断与操作再拆成两类能力对象。

## 验证要求与自举

用正常任务、必要输入缺失、相邻能力边界和典型失败检验定义。记录预期、实际过程与产物、结果、限制和修订依据；仅有预期和示例不算已测试。结构核验、情境走查、真实使用及独立测试分别记录。

有持久数据时按共享方法验证默认、保存后采用、临时覆盖、必要状态更新、清除及错误保留，观察专业分支和实际输出是否符合字段含义。无需求时确认不建立多余记录；程序格式校验不能替代语义验证。

设计本基本功自身时同样检查独立结果、方法和标准，引用当前已确认依据及用户决定形成候选。候选可在明确范围内试用，但不能因自检通过自动取得长期有效性或变更其他规则的权力。

当前可由 Agent 读取、分析、编辑和检查完成本设计方法。需要固定程序支持时直接使用经过核实的脚本或 CLI。是否达到可用及验证覆盖范围，由实际证据说明，不自行推进不存在或未获确认的状态制度。
