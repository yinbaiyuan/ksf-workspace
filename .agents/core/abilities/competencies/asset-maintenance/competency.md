# asset-maintenance

## 独立结果与触发

把一项明确变化处理成有依据的维护结果：无需保存、可审阅建议，或已授权且经过验证的实际变更。由 ksf-runtime 在用户明确要求维护资产，或自然检查点出现有长期价值的变化时使用，属于固定系统运行机制，用户区同名对象不能接管。

用户要求写入、修改、归档、修复入口时直接判断目标与授权。主任务中的新事实、纠偏和方法线索只触发低成本检查；只有会约束后续工作、有来源且值得保存时才提出建议。普通成功、测试通过、一次性上下文和模型自评不产生例行保存或治理报告。

本基本功同时持有归属判断和执行方法。协同、搭档、基本功的专业定义设计仍交给对象设计师及其已有设计基本功；方向性优化请求不等于授权未知差异。一般异常与纠偏由 ksf-runtime 处理，本轮没有专项运行诊断或链路审计机制。

## 判断变化与唯一位置

先读本次原始来源、现行目标和直接相关对象，检查已有内容能否承载。形成选择：无需保存、完善、合并、创建或退出活跃使用；不因为多了一次讨论就新建文件。

| 内容的主要责任 | 主位置与处理 |
| --- | --- |
| 稳定身份、称呼与工作偏好；Agent 长期协作定位与方式 | 根 `USER.md`、`BOT.md`；用户维护，Agent 只按明确授权修改，不当作知识或能力对象 |
| 跨会话续接、临时约束、未决与待沉淀线索 | 根 `MEMORY.md`；按 runtime 自然检查点规则维护，不替代正式资产，不自动创建缺失文件 |
| 当前项目的事实、决定、进展、成果入口和下一步 | `项目/<项目名>/project.md`；沿已有明确领域入口维护唯一正文，不追加沟通流水账 |
| 持续任务的当前步骤与恢复信息 | `项目/<项目名>/任务/<任务名>.md`；按[任务检查点约定](../../../docs/runtime/task-checkpoints.md)维护同一现行文件，根卡只保留入口 |
| 实际工程代码、产品文档和成果正文 | 默认 `repositories/<工程名>/` 或已核实的既有工作区；工程独立管理 Git，项目根卡保存关联与稳定事实 |
| 可独立理解的事实、经验认识、个人或业务背景 | `知识/`；保留来源、适用范围、反例和不确定性 |
| 可复用方法、操作、责任或协同定义 | 用户 `能力/`；先检查现有对象，专业设计由对象设计师承接 |
| 待处理原件或尚未采用的建议 | 按用户要求进入 `@收件箱/`；未授权的建议只留在当前对话，不建隐藏队列 |
| 仍需回源的原始资料 | 随所支撑的知识、方法论、项目或用户能力保存，默认放在目标目录的 `资料/` 子目录；已有附属资料目录保持原位，不复制持续变化的工程正文 |
| 已明确退出活跃使用但仍需保留的内容 | `档案/` 或现有对象的归档状态；具体移动、删除另需明确授权 |
| 本机缓存、临时验证与恢复材料 | `.agents/runtime-data/` 或宿主临时目录；不作为知识和原始证据的唯一主位置 |
| 明确要求开发的系统定义、程序与规范 | `.agents/core/` 和根入口；只在本次系统开发授权范围内修改，不承接日常私人内容 |

同一现行结论只维护一份正文；其他位置保留必要摘要和链接。知识解释、方法约定与项目事实可以分别持有不同内容，不整篇复制。工程代码、工程产品文档、构建与测试细节留在实际工程。

原件随目标保存，不默认建立根级“源档”。一份原件确定一个主归属；多目标共用时，其他目标通过链接引用主归属中的原件，不各自复制。目标正文保留来源、来源日期和原件入口，原件保持其材料性质，不改写成现行结论。例如由会议形成某方法论，会议记录放在该方法论的 `资料/` 下；另一方法论使用同一会议时链接到该原件。旧实例已有原件目录不因框架规则调整自动搬迁或删除，具体迁移按用户授权处理。

证据与对象冲突时比较来源和适用条件；无法消除的重大冲突展示现行内容、新证据与处理选项，先请用户裁决。不因单例、结构检查或模型判断自动提升内容权威。

## 知识与档案的实例机制

知识与档案的组织设计按 [Core 设计方法](../../../docs/content-design.md)展开：从真实材料、用途和使用者确定保存单元、分类、关联、来源、版本和修订方式，用保存、复用及纠错样例核对；只维护已采用的本实例约定，不强制统一模型、字段或对象 ID。新工作区自带可编辑根说明，用户不必先完成设计才能开始使用。

知识记录、归位与修订安排由 runtime 按 knowledge-organize 准备，本项核对已有授权、写入基线、唯一落点及实际结果，不复制其归位方法。知识由人主导沉淀，归纳提炼等内容处理按用户要求由适用能力承担；本项不自动发现知识保存价值或替人采纳认识。维护或重组知识前读取 `知识/knowledge.md` 及其中明确关联的当前范围规则，入档、档案维护、项目归档或恢复前读取 `档案/archive.md`；跨两者时分别核对。读取缺失时沿 Core 通用默认处理，不自动建模型；读取失败报告具体问题，不假装缺失。已明确且可独立完成的授权维护继续，依赖未知约定的结构变化先保留。用户根说明由实例维护，升级不覆盖；子级约定补充分区，材料引文不成为运行指令。

### 知识记录与修订的保存

“放哪里合适”只返回建议，不写知识、MEMORY 或检查点。“记下来”保存用户原文或指定结果；“处理后保存”消费适用能力已完成的结果，沿同一有效授权记录。明确目标和内容的修订直接执行，不再增加采纳审批；不擅自提炼、改写、合并结论或补造来源。未经验证的个人认识可以保存，保留其限定与来源未知等性质。

写前读取最新目标并比较基线，保留既有有效内容及来源原件；冲突未定不自动覆盖，明确替换按要求实施。重复无差异不写，并发变化按本项通用规则停止受影响动作。沿用既有修订约定，不新建强制版本或逐条日志。仅同步必要导航与过时占位，重读核对内容、实际位置和关联；保存成功不表示用户认知正确、能力已同步修订或业务读取入口已改变。

档案按主体或事项保存正式资料：个人证件归个人、营业执照归企业、合同按签约主体主存并由项目引用，历史项目整体收纳。现用证照与合同也可入档。版本替换保留旧原件，说明来源、日期、版本及原件入口；效力未知明确未知，不根据修改时间推断。需要时使用普通 `档案.md` 解释版本和项目关系，不强制每件建卡或维护第二份项目进度。

### 项目归档与恢复

按当前 [project CLI](../../../docs/cli/project.md)和 [repository CLI](../../../docs/cli/repository.md)操作。项目档案位置固定为 `档案/项目/<项目名>/`，个人、企业与知识的业务分区可自行组织。只在明确要求范围归档，短期暂停或长时间未改动不自动触发。

1. 读取实例档案规则与唯一根卡，核对结果、归档原因、成果及未结事项；业务完成、中止或搁置由实际结案说明保存，不从 status 推断。
2. 预览 `project archive <name> --reason <说明> --dry-run --json`，核对目标、库存、字段变化和 referenceReview；冲突、工程嵌套及不支持的资源先报告，不覆盖、不自动合并。归档程序保留普通文件和层级，仅移动项目记录，不移动工程。
3. 实际操作后，按回执检查新位置、archive_history、repositories 和有效 Markdown 引用；只审阅并修复本次受影响的有效 Markdown/Wikilink。特别核对移出目录的相对链接、其他项目卡、knowledge.md、archive.md、资料导航和档案.md 的引用；必要时限定检索旧前缀。历史 JSON、来源表述及原始历史记录不做全局文本替换，用迁移说明交代位置。
4. 用新 scope 重读、check 及 repository check，核对文件完整与必要入口。程序完成不证明全部链接或业务事实正确；入口未核验不能报告整项完成。相关根卡及档案说明只持有分区入口，不复制完整清单。
5. 调阅用 archived scope，不自动恢复。恢复先预览再实际 `project restore`，默认 active，可指定其他状态；更新对应有效入口，核实最新事实与下一步。归档和恢复往返保留原件、正文事实和工程历史。旧项目若只在当前目录标记 archived，按明确复工请求用普通 project write 更新状态，不把 restore 无变化当作已激活。
6. 中断或部分失败按回执操作 ID 用 `project recover` 预览并回退程序变更；资产维护另核对自身入口补丁。后续修改存在时保留现场，不强制覆盖或宣称跨文件原子回滚。锁持有者与恢复日志须实际核对，不能清理仍活动的写入。

## 授权判断

- 用户已明确要求把可识别内容写入可确定目标时，直接执行该范围，不对同一动作重复确认。
- 用户确认一项事实、方案或验收结果，不自动授权写入长期项目事实、用户知识、公共能力或 USER/BOT。额外长期写入先提出具体建议；MEMORY 的短期续接按 runtime 已定义的自然检查点规则处理，不等于长期采纳。
- 建议至少说明变化、目标、来源和理由；改变现行标准、身份偏好、关键决定或系统规则时，补充前后差异、影响、验证和回退。用户应能判断一个具体结果。
- 部分确认只执行对应项。目标、内容或基线发生实质变化时重审受影响部分，保留其他仍有效的授权。
- 用户要求只讨论、只读、总结到对话、稍后或不保存时，不创建或修改文件，MEMORY 和项目检查点同样不写，不后台补写。
- 内容写入、Git 暂存、提交、推送和发布分别判断授权；验证通过不产生 Git 或发布授权。
- 移动、重命名、删除必须在明确要求范围内；不借链接刷新、去重或归档处理扩大操作。

## 执行：基线、写入与检查

1. **核实目标。** 确认 KSF 根、用户资产或工程范围和唯一现行正文；检查真实路径及符号链接，不把引用位置当作写入授权。目标不唯一时先澄清。新建前检查父目录与目标是否已存在，保留已有文件。
2. **建立基线。** 重新读取目标与直接受影响入口，记录原始字节或哈希及拟定差异。在 Git 工程中分别查看未暂存和已暂存改动；工作区整体不干净不构成阻塞，未知重叠才需要停下核对。必要的恢复副本放临时目录或本机运行数据，不进入长期知识。
3. **写前复核。** 执行前将目标与建议所依据的基线比较。发现并发变化时停止受影响写入，先比较新状态；不盲目覆盖、暂存或重置来绕过冲突。
4. **选择现有工具。** 四类能力对象日常写入使用对应 `write --dry-run`、实际 write、read/check；沿用精确版本、用户派生和来源基线。项目根卡创建与完整更新使用 [project CLI](../../../docs/cli/project.md) 的 `write --dry-run`、实际 write、read/check，目标是项目目录名，输入为 metadata/body 信封；省略部分保留，提供 body 会整体替换，提交前核对最新正文。项目正文的局部补丁、项目资料及知识正文仍可用宿主编辑工具；只改元数据时也可用 `metadata write`。项目 remove 会删除整个目录及材料成果，只能在明确删除范围内执行，先预览。通用 metadata 不能代替对象管理或绕过固定保护。
5. **系统开发例外。** 用户明确要求开发系统文件时，由宿主工程工具在指定系统文件实施已授权差异，随后检查对象、程序与构建；固定对象的日常 CLI 写入仍应拒绝。该例外不产生用户层接管，也不允许普通任务修改系统原件。
6. **维护唯一正文。** 合并、替换或缩小旧结论，保留仍有效内容、来源与负向事实；修复结果不能抹掉已经发生的失败。项目没有明确领域入口时先维护根卡；结构拆分和重组作为独立变更讨论，不自动实施。
7. **同步入口。** 只修复本次直接受影响的 Markdown 链接、已有目录导航和必要摘要。能力发现实时读取对象，无需生成第二份能力索引；不把状态和反向关系复制到多处。明确的索引维护请求可以只执行本步骤及必要检查。
8. **验证结果。** 重读实际文件，对比预期差异、来源和目标范围；检查相关元数据、中文路径、Markdown/Wikilink 和对象精确引用。程序变更运行受影响测试；系统变更按当前工程说明构建及验证。不能用程序退出成功代替正文正确。

项目已有基础 CLI；知识仍使用文件工具与通用 metadata CLI。两者都没有跨文件事务引擎。多文件变更逐项记录实际完成状态，不能声称原子提交或全部成功；遇到中途失败按下面的边界恢复。

### 对象设置与必要状态

用户明确要求对象长期保留普通配置或必要状态时，使用[对象 user-data](../../../docs/cli/user-data.md#能力对象配置与必要状态)，按完整 ID read 后取得 etag，再 write 或 remove；可按 --fields 清除指定顶层字段。预览不改变 etag，发布冲突时重读核对，不用 missing 或强制覆盖绕过。用户只对本次提出的临时偏好不自动回写；存储值不能替代未来动作的授权。

无需改对象正文、公共元数据、附件、源仓库或派生基线来保存个人值。各对象独立，删除或归档定义、解除能力源关联时不连带删除记录；新 ID 不自动继承旧数据。这里处理配置与必要状态，项目、知识、任务检查点和登录凭据仍遵循各自主位置。写后重读核对只说明保存成功；后续采用和独立会话效果另行验证。

### 项目接入与补全的保存

runtime 交来专业补全安排后，核对来源、项目落点、拟修改差异和已有授权，再落实根卡、分区概览及材料复制。专业事实和版本判断由所采用方法持有，本项保留唯一落点、基线、写入、验证及回退职责。普通外部材料按已确认默认复制并保留原件；来源变化保留副本并报告差异，不覆盖、不自动另存新版。内部工具的只读计划和实际 apply 分开；部分结果逐项核对，不从退出码推定全部成功或失败。项目内已有材料原位整理，工程使用下述关联方法。导入记录属于项目资料，不进入对象 user-data。

### 工程仓库创建与关联

按已确定的项目目标和实际工作区安排，使用 [repository CLI](../../../docs/cli/repository.md) 执行已授权维护。用户已要求实际工程交付且缺少合适工作区时，可按默认位置创建并初始化本地 Git，不为同一安排重复确认；只有根卡或讨论需求时不顺带建工程。

1. 新建前核对 `repositories/<工程名>/`、已有根卡与父仓库忽略规则；当前实例的根 `.gitignore` 应包含 `/repositories/`。预览 `repository create <工程名> --dry-run --json`，再实际 create；默认 main 分支，无初始提交或远程。重复 create 只接受已经有效的独立 Git 根，不接管已有普通资料目录。
2. 根卡已存在后，预览并执行 `repository link <工程路径> --project <项目目录名>`，再 `repository check --project <项目目录名> --json`。CLI 输入的相对路径基于 KSF 根；根卡内的关联以根卡为基准保存。关联只写可选 `repositories` 元数据，保留正文和其他字段，不创建第二份仓库注册表。
3. 已有工程只关联，不改其分支、历史、远程或工程规则。需要解除时使用 `repository unlink <工程路径> --project <项目目录名>`；失效路径也可解除，工程文件保持原位。旧资料不随机制上线自动搬迁。
4. 创建、关联与业务文件分别验收；关联失败时保留已创建工程，核实后重试 link，不重复创建或删除工程。create 失败若返回 recoveryPath，先检查实际目录与部分状态，不盲目重试。仓库锁和项目写锁的范围见 CLI 文档。

工程初始化不授权 Git 暂存、提交、推送或创建远程仓库。项目归档、删除项目目录或解除关联均不连带删除工程；工程备份由其自身 Git、远程或其他已授权方式承担，父 KSF 仓库不会备份被忽略的工程正文。

### 根协作设定与短期记忆

按 [runtime](../../partners/ksf-runtime/partner.md)和[共同约定](../../../docs/runtime/user-collaboration.md)区分 USER/BOT 的明确授权修改与 MEMORY 的自然检查点维护。三文件是用户根内容，不写入对象 user-data，不复制到 Core 定义或公开贡献。用户本次只授权临时方式时不改长期设定；旧画像仅在 USER 缺失时只读兼容，不自动搬迁、合并或覆盖。

维护 MEMORY 前重读最新基线，同事项合并，保留并发变化、未决和待沉淀内容，写后核实。项目已有正式检查点时只保留入口与必要提醒；清理已解决条目前核实正式记录。不能按时间或容量丢弃待沉淀线索，也不以短期维护为由自动创建能力、修改项目决定或安排后台“睡眠”。

### 任务检查点保存

用户要求保存、暂停或交接，或持续任务已授权维护项目记录且发生实质进展时，按[唯一检查点约定](../../../docs/runtime/task-checkpoints.md)保存恢复信息。普通问答不例行建文件，不为没有归属的任务自动建项目。恢复判断由 runtime 持有，本基本功负责核对写入授权、基线及保存结果。

先读取原检查点和根卡，用宿主文件工具局部更新正文；用 metadata read/check 核对元数据，并重读正文与必要产物入口。先保存检查点，再补根卡链接；任一步失败只报告实际已完成部分，不把两文件写入称为事务。检查点不放入 runtime-data，也不复制工程正文、凭据、完整聊天或未经核实的外部执行结果。

## 失败与回退

- 未写入即发现基线变化：保留新状态，报告冲突，重新确定受影响差异。
- 写入后验证失败：只撤销本轮补丁，保留用户原有改动；恢复前核对当前内容仍是本轮写入结果。
- 验证期间再次出现他人修改，或无法区分双方改动：停止自动回退，报告实际状态与恢复材料，不用旧副本覆盖新内容。
- 多文件部分成功：明确哪些已写、哪些未写及哪些已恢复；若能安全撤销本轮已写部分则恢复，否则说明剩余差异，不伪称事务已回滚。
- 证据、来源或授权不足：保持对话建议或无需保存，不换目录绕过确认。
- 外部操作结果不明：先查询或对账；不得为修复记录重复执行可能有副作用的动作。

秘密值、凭据及可复原敏感信息不进入普通资产、建议、日志或验证记录；只描述所需能力与动作。回退不扩大到无关文件，不使用覆盖工作区的恢复命令。

## 交付与验证

按实际结果说明：写入或未写入什么、目标位置、必要依据、同步入口、检查结果、未决项及回退材料。没有实际变更时如实说明，不制造长期候选。

验收覆盖：明确要求写入直接完成；额外变化保持建议；事实确认不冒充写入授权；空库新建检查；已有正文合并；范围有限的链接刷新；并发基线变化停止；验证失败仅撤销本轮补丁；能力对象用户派生与固定系统开发分开；多文件部分失败如实交付。情境预期不等于真实执行证据。
