# asset-maintenance

## 独立结果与触发

把一项明确变化处理成有依据的维护结果：无需保存、可审阅建议，或已授权且经过验证的实际变更。由 ksf-runtime 在用户明确要求维护资产，或自然检查点出现有长期价值的变化时使用，属于固定系统运行机制，用户区同名对象不能接管。

用户要求写入、修改、归档、修复入口时直接判断目标与授权。主任务中的新事实、纠偏和方法线索只触发低成本检查；只有会约束后续工作、有来源且值得保存时才提出建议。普通成功、测试通过、一次性上下文和模型自评不产生例行保存或治理报告。

本基本功同时持有归属判断和执行方法。工作流、搭档、基本功的专业定义设计仍交给对象设计师及其已有设计基本功；方向性优化请求不等于授权未知差异。一般异常与纠偏由 ksf-runtime 处理，本轮没有专项运行诊断或链路审计机制。

## 判断变化与唯一位置

先读本次原始来源、现行目标和直接相关对象，检查已有内容能否承载。形成选择：无需保存、完善、合并、创建或退出活跃使用；不因为多了一次讨论就新建文件。

| 内容的主要责任 | 主位置与处理 |
| --- | --- |
| 当前项目的事实、决定、进展、成果入口和下一步 | `项目/<项目名>/project.md`；沿已有明确领域入口维护唯一正文，不追加沟通流水账 |
| 可独立理解的事实、经验认识、个人或业务背景 | `知识/`；保留来源、适用范围、反例和不确定性 |
| 可复用方法、操作、责任或协同定义 | 用户 `能力/`；先检查现有对象，专业设计由对象设计师承接 |
| 待处理原件或尚未采用的建议 | 按用户要求进入 `@收件箱/`；未授权的建议只留在当前对话，不建隐藏队列 |
| 仍需回源的原始资料 | `源档/`；不把原件改写成现行结论，不复制持续变化的工程正文 |
| 已明确退出活跃使用但仍需保留的内容 | `归档/` 或现有对象的归档状态；具体移动、删除另需明确授权 |
| 本机缓存、临时验证与恢复材料 | `.agents/runtime-data/` 或宿主临时目录；不作为知识和原始证据的唯一主位置 |
| 明确要求开发的系统定义、程序与规范 | `.agents/core/` 和根入口；只在本次系统开发授权范围内修改，不承接日常私人内容 |

同一现行结论只维护一份正文；其他位置保留必要摘要和链接。知识解释、方法约定与项目事实可以分别持有不同内容，不整篇复制。工程代码、工程产品文档、构建与测试细节留在实际工程。

证据与对象冲突时比较来源和适用条件；无法消除的重大冲突展示现行内容、新证据与处理选项，先请用户裁决。不因单例、结构检查或模型判断自动提升内容权威。

## 授权判断

- 用户已明确要求把可识别内容写入可确定目标时，直接执行该范围，不对同一动作重复确认。
- 用户确认一项事实、方案或验收结果，不自动授权写入项目记忆、用户知识或公共能力。额外长期写入先提出具体建议。
- 建议至少说明变化、目标、来源和理由；改变现行标准、身份偏好、关键决定或系统规则时，补充前后差异、影响、验证和回退。用户应能判断一个具体结果。
- 部分确认只执行对应项。目标、内容或基线发生实质变化时重审受影响部分，保留其他仍有效的授权。
- 用户要求仅讨论、总结到对话、稍后或不保存时，不创建文件，不后台补写。
- 内容写入、Git 暂存、提交、推送和发布分别判断授权；验证通过不产生 Git 或发布授权。
- 移动、重命名、删除必须在明确要求范围内；不借链接刷新、去重或归档处理扩大操作。

## 执行：基线、写入与检查

1. **核实目标。** 确认 KSF 根、用户资产或工程范围和唯一现行正文；检查真实路径及符号链接，不把引用位置当作写入授权。目标不唯一时先澄清。新建前检查父目录与目标是否已存在，保留已有文件。
2. **建立基线。** 重新读取目标与直接受影响入口，记录原始字节或哈希及拟定差异。在 Git 工程中分别查看未暂存和已暂存改动；工作区整体不干净不构成阻塞，未知重叠才需要停下核对。必要的恢复副本放临时目录或本机运行数据，不进入长期知识。
3. **写前复核。** 执行前将目标与建议所依据的基线比较。发现并发变化时停止受影响写入，先比较新状态；不盲目覆盖、暂存或重置来绕过冲突。
4. **选择现有工具。** 四类能力对象日常写入使用对应 `write --dry-run`、实际 write、read/check；沿用精确版本、用户派生和来源基线。项目根卡创建与完整更新使用 [project CLI](../../../docs/cli/project.md) 的 `write --dry-run`、实际 write、read/check，目标是项目目录名，输入为 metadata/body 信封；省略部分保留，提供 body 会整体替换，提交前核对最新正文。项目正文的局部补丁、项目资料及知识正文仍可用宿主编辑工具；只改元数据时也可用 `metadata write`。项目 remove 会删除整个目录及材料成果，只能在明确删除范围内执行，先预览。通用 metadata 不能代替对象管理或绕过固定保护。
5. **系统开发例外。** 用户明确要求开发系统文件时，由宿主工程工具在指定系统文件实施已授权差异，随后检查对象、程序与构建；固定对象的日常 CLI 写入仍应拒绝。该例外不产生用户层接管，也不允许普通任务修改系统原件。
6. **维护唯一正文。** 合并、替换或缩小旧结论，保留仍有效内容、来源与负向事实；修复结果不能抹掉已经发生的失败。项目没有明确领域入口时先维护根卡；结构拆分和重组作为独立变更讨论，不自动实施。
7. **同步入口。** 只修复本次直接受影响的 Markdown 链接、已有目录导航和必要摘要。能力发现实时读取对象，无需生成第二份能力索引；不把状态和反向关系复制到多处。明确的索引维护请求可以只执行本步骤及必要检查。
8. **验证结果。** 重读实际文件，对比预期差异、来源和目标范围；检查相关元数据、中文路径、Markdown/Wikilink 和对象精确引用。程序变更运行受影响测试；系统变更按当前工程说明构建及验证。不能用程序退出成功代替正文正确。

项目已有基础 CLI；知识仍使用文件工具与通用 metadata CLI。两者都没有跨文件事务引擎。多文件变更逐项记录实际完成状态，不能声称原子提交或全部成功；遇到中途失败按下面的边界恢复。

## 失败与回退

- 未写入即发现基线变化：保留新状态，报告冲突，重新确定受影响差异。
- 写入后验证失败：只撤销本轮补丁，保留用户原有改动；恢复前核对当前内容仍是本轮写入结果。
- 验证期间再次出现他人修改，或无法区分双方改动：停止自动回退，报告实际状态与恢复材料，不用旧副本覆盖新内容。
- 多文件部分成功：明确哪些已写、哪些未写及哪些已恢复；若能安全撤销本轮已写部分则恢复，否则说明剩余差异，不伪称事务已回滚。
- 证据、来源或授权不足：保持对话建议或无需保存，不换目录绕过确认。
- 外部操作结果不明：先查询或对账；不得为修复记录重复执行可能有副作用的动作。

秘密值、凭据及可复原敏感信息不进入普通资产、建议、日志或验证记录；只描述所需能力与动作。回退不扩大到无关文件，不使用覆盖工作区的恢复命令。

## 交付与验证

按实际结果说明：写入或未写入什么、目标位置、必要依据、同步入口、检查结果、未决项及回退材料。没有实际变更时如实说明，不制造长期候选。

验收覆盖：明确要求写入直接完成；额外变化保持建议；事实确认不冒充写入授权；空库新建检查；已有正文合并；范围有限的链接刷新；并发基线变化停止；验证失败仅撤销本轮补丁；能力对象用户派生与固定系统开发分开；多文件部分失败如实交付。情境预期不等于真实执行证据。
