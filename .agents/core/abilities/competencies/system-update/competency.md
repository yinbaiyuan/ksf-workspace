# 系统版本维护

## 结果、输入与边界

将指定 KSF 根、请求的操作、可用发行源或指定更新包、当前系统差异和有效授权，转成有证据的版本状态或已验证的版本切换。查询结果、可执行预览、成功安装及失败未改变各是不同结果。Core 源码开发与新实例创建不使用安装流程代替。

先核对根目录及本地来源。`system read --json` 返回开发模式时，不把 Core 开发源当成发行实例升级。未知版本、平台或来源先查明；没有安装授权时只查询和预览。CLI 使用该根的绝对入口，业务工作目录不决定 KSF 根。

## 方法

1. **读取现状。** 运行 `.agents/ksf system read --json`，核对 installed、version、core、changes、backups 与 errors。`automaticUpdates` 应为 false。小型发行凭据固定版本和准确 Core 提交；read 为比较系统差异会联网读取该原版的完整文件树，不查询最新版本。禁止手工改写来源来消除差异。
2. **检查更新。** 仅在用户要求时运行 `system check --json`；指定源使用 `--source`。核对平台、版本、来源与 available；同版本不同来源拒绝，旧版本不安装。请求失败或索引不可信时报告查询失败，保持现有版本，不把失败当作已是最新。
3. **预览升级。** 明确要求升级后运行 `system update --dry-run --json`，指定源或更新包分别用 `--source` 或 `--from`，两者互斥。检查文件变化和 conflicts；预览不是冻结安装计划，实际执行会重新校验。任何重叠冲突先保留内容并解决，不能删除本地编辑来强行通过。差异实质超出原授权时先澄清新增部分。
4. **安装与验收。** 已授权且可执行时运行同目标的 `system update --json`。程序核对校验和、受限归档、固定提交的远程原版、本地及新版；仅合并需要时读取并校验原文，验证候选运行时、语法和系统定义，再执行事务切换。核对 changed、from、to、backup；随后重新 read 并检查实际版本、入口和必要对象。重读定义后再恢复任务，不把退出码单独当作全部验收。
5. **回滚。** 用户明确要求时先 `system rollback --dry-run --json`，再执行 `system rollback --json`。回滚针对最近备份；升级后有新增系统编辑时报 `ROLLBACK_LOCAL_CHANGES`，先保存或贡献这些差异，不绕过保护。按安装同样检查实际版本与定义。
6. **失败恢复。** 固定启动器先恢复中断事务。`UPDATE_BUSY` 保留活跃事务；`RECOVERY_CONFLICT` 保留当前文件和快照供核对，不盲目重试覆盖。已提交事务只完成归档；未提交事务只恢复本事务实际替换的内容。恢复不依赖 Git、网络或完整 Core。只有恢复结果和版本已核实，才报告恢复成功。

`system sync [--quiet]` 是保留的显式检查并更新入口，仍使用已有间隔缓存，可能返回 not-due；用户明确要立即升级时采用 update。启动与普通 CLI 不调用 sync，`KSF_SKIP_AUTO_UPDATE` 为无作用兼容项，不是安装授权。

## 输出与质量

交付操作类型、实际根与来源、前后版本、变化或冲突路径、备份、验证结果和未决项。用户项目、知识、能力、Git 配置、README 与忽略规则不因版本切换被改写。程序协议与参数见[system CLI](../../../docs/cli/system.md)、[发行协议](../../../docs/distribution.md)及[启动器](../../../runtime/launcher.md)。

模拟正例：用户要求升级，预览无冲突，安装后版本和入口均核实。反例：看到 available=true 就安装。边界例：只有“查一下新版”或查询失败，保留当前版本；中断恢复完成不发起下一次升级。通过隔离正常、冲突、坏定义、中断与并发编辑场景验证；程序证据和 Agent 走查分别记录。
