# Git 提交信息规则

本规则用于开发提交的标题与正文，以及贡献流程生成的 Core 提交。提交信息应让后续维护者知道为什么改、行为如何变化、验证到什么程度。Git 操作与系统／用户边界仍遵循[Git 协作规则](git.md)；PR 说明可复用已核实的事实。

## 标题

```text
<type>(<scope>)[!]: <中文动作摘要>
```

type、scope 使用小写英文。摘要默认中文，以具体动作说明结果，例如“增加”“修复”“拒绝”“移除”“统一”。一个提交围绕一个可独立解释的目的；无关目的先拆分。

标题建议不超过 50 个 Unicode 码点，硬上限为 72 个，包含前缀；不按 UTF-8 字节数或终端显示宽度计数。末尾不加句号、感叹号、问号或分号，不使用“更新代码”“优化逻辑”“修复问题”等泛化摘要。

| type | 使用条件 |
| --- | --- |
| feat | 增加可用能力或行为 |
| fix | 修复不符合预期的行为 |
| refactor | 调整内部结构，保持对外行为 |
| docs | 修改说明文档，不改变运行行为 |
| test | 增加或调整测试 |
| perf | 改善性能，并有对应依据 |
| build | 修改构建或依赖 |
| ci | 修改持续集成 |
| chore | 其他维护事项，不替代更准确的类型 |
| revert | 撤销已有提交，正文指出撤销对象及原因 |

scope 表示主要受影响模块，使用小写字母开头的英文或连字符名称，例如 project、routing、user-data、contribute、release。多个关联模块选择共同的主要模块，不在范围中堆叠文件名。scope 不是固定枚举，新增范围按实际责任命名。

工作流、搭档、基本功和数据包按行为判断类型。Markdown 中的执行约定改变运行行为时，应按实际目的使用 feat、fix 或 refactor，不能仅按扩展名归为 docs。

```text
fix(project): 防止项目根卡覆盖并发修改
feat(user-data): 支持按对象保存持久设置
docs(git): 明确提交说明的生成规则
```

以上是格式示例，不是对应改动或验证的完成记录。

## 正文与尾注

标题后空一行，按顺序填写以下三个部分，名称及全角冒号固定，每项恰好出现一次，内容不能为空。小改动可各写一句。

| 部分 | 必须说明 | 内容依据 |
| --- | --- | --- |
| 原因： | 原有问题、触发情境或修改动机 | 已确认需求、问题证据或明确的维护目的 |
| 变更： | 本次提交后的具体行为及必要取舍 | 本次提交差异及相关源码／定义 |
| 验证： | 实际执行的命令或检查、结果及覆盖范围 | 对应执行记录；未执行时写明原因 |

变更不逐个罗列文件或抄写代码。验证不得把未运行、历史结果、推演或计划写成“通过”；检查格式通过也不能代替行为验证。测试后若待提交内容变化，需要判断结果是否仍适用。

存在兼容性变化或明确剩余问题时，可在必填正文后增加“兼容性：”“剩余问题：”。破坏性变更必须同时在标题 scope 后加入 !，并在正文后空一行添加 `BREAKING CHANGE: <影响及迁移要求>` 尾注，说明受影响旧用法、替代方式与迁移。普通变更不填无意义的占位章节。Issue 等尾注只填写真实关联。

## 生成与内容检查

1. 确定提交范围。普通本地提交以暂存区差异为准；已有提交以指定提交或提交区间为准；Core 贡献以贡献计划中的选定系统差异为准，不直接复制个人提交说明。
2. 读取差异、相关上下文、已确认需求和实际验证记录。原因不从文件名猜测，变更不加入计划中的功能，验证不从“有测试文件”推断通过。
3. 依据行为选择 type、scope 和破坏性标记，再按模板生成正文。缺少会影响判断的原因或兼容性信息时补查，仍不能确定则提出具体问题。
4. 执行格式检查，再逐条对照差异与证据，核对语义、提交边界、兼容性和迁移要求。格式工具不能证明内容真实或信息适合公开。
5. 提交前重新核对暂存区或冻结计划。提交内容变化后重审说明与验证结果；新贡献计划必须重新审阅完整消息和 digest。

稳定生成指结构、类型判断依据和事实范围一致，不要求每次措辞逐字相同。

## 模板与校验

完整填写模板位于 [commit-message.txt](templates/commit-message.txt)，包含标题和必填正文。填写时替换尖括号内容，破坏性标记只保留实际需要的 !，删除方括号。它是待填写输入，原样使用会校验失败。

下面是一份完整的格式示例；其验证栏明确标注为演示，不作为实际提交或测试记录：

```text
docs(git): 规定提交信息的填写和检查方式

原因：
提交说明需要统一结构，并能回到实际差异和验证依据。

变更：
- 规定标题、原因、变更和验证的填写方式。
- 将格式检查与内容核对分别说明。

验证：
- 未执行：本段仅演示消息格式，不代表实际提交或测试结果。
```

```sh
.agents/ksf commit-message template
.agents/ksf commit-message check --from /tmp/commit-message.txt --json
```

[commit-message CLI](cli/commit-message.md)检查支持的标题类型、范围语法、长度、标点、泛化摘要、必填正文及顺序、明显占位符、控制字符和破坏性标记／尾注。超过 50 码点只提示，超过 72 码点失败。它不判断中文文风、模块是否准确、修改是否兼容、验证陈述是否真实，也不能识别任意形式的占位文字；这些仍按上节检查。

Agent 通过 `git commit -m/-F` 或 API 创建开发提交，也必须遵循同一规则。Git 的 commit.template 只辅助编辑器填写，不约束 -m/-F。当前命令不自动安装 Git hook 或修改本地／全局配置；开发提交前由 Agent 主动执行 check，贡献 prepare 则在程序内强制校验。

## Core 贡献

prepare 必须明确提供标题及完整正文，支持 `--body` 或 `--body-file` 二选一；正文文件不包含标题。程序在 Git／网络读取前校验，拒绝泛化默认标题或缺少必填字段的说明。原因、变更和验证由 Agent 根据选定公开内容整理，程序不代编动机或测试结论。

新计划 schema_version 为 4，冻结完整 commitMessage 并纳入 digest。read、submit dry-run 和审阅输出均可检查同一份文本，真实提交使用该文本作为完整 Git message，不从个人 Git 历史取正文。PR 与 Git 共用标题，正文按[PR 说明规则](pr-description.md)单独提供并冻结，包含 prepare 阶段生成的来源说明。首次发布前修改消息须重新准备和审阅，已发布内容不在重试时自动改写。

旧 schema 1／2／3 计划保持可读；已记录发布的计划只读核对已有 PR，不改写旧消息。未发布旧计划须按新规则重新准备，不在旧审阅摘要下补造正文。schema 3 的冻结消息仍在远程核对，保持原有重复 PR 和失败恢复保护。

## 依据

本规则采用 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) 的标题与破坏性变更形式，参考 [Git 贡献指南](https://git-scm.com/docs/SubmittingPatches)的简短动作标题及原因说明。scope 必填、中文默认、72 码点上限、三项必填正文和同时使用 ! 与尾注属于 KSF 自身约定；不据此自动决定版本或触发发行。
