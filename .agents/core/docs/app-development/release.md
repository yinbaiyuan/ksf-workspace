# 发布、升级与兼容

## 应用源与版本

KSF 固定启用[公共默认应用源](https://yinbaiyuan.github.io/ksf-apps/index.json)，由 [ksf-apps 仓库](https://github.com/yinbaiyuan/ksf-apps)通过 GitHub Pages 发布。此源不能通过界面或公共 API 改名、改地址、停用或移除；服务端返回 `APP_SOURCE_LOCKED`（403）。这是宿主配置规则，不是操作系统级文件保护。

Core 自带应用统一由固定的 KSF 公用应用源（ksf-apps）接管升级；随包目录仅是同一来源的内部离线资源，不再列独立来源。旧 builtin 安装来源自动备份并迁至 ksf-apps，保留安装身份、启用状态和数据，自定义来源保留。断网时显示已验证缓存或随包基线及上次检查时间，明确最新版本尚未确认。同 ID、版本、平台的远程文件与离线文件摘要必须一致，冲突时停止安装。Core 升级保留较新且兼容的应用，不自动降级。应用贡献见仓库的 CONTRIBUTING.md；线上接管以发布后回读和真实升级为准。

用户可在应用商店直接导入 `.ksfapp`，无需索引或联网。手动安装与应用源安装共用包校验、不可变版本、数据目录、任务租约和延迟切换；操作方式见[快速开始](quickstart.md#分享应用包并手动安装)。手动来源不检查远程更新，升级由用户导入新版包；源安装与手动安装之间不自动换源。离线包只能与本机已知兼容版本比较，不能据此确认开发者全球最新版本。

构建输出 .ksfapp 与ksf-app-registry-v1的index.json。索引每项包含manifest和package.url/size/sha256；包URL相对索引解析。HTTP(S)源由本机宿主下载，不需要浏览器CORS；首版不支持URL内凭据和自动跟随重定向。

必须在执行包或Manifest变更时递增版本；仅商店展示资料变化可以独立发布，见[商店资料](store-listing.md)。打包器及安装器拒绝同版本换内容（包含pending、可回退及卸载后保留的历史包）；不可通过覆盖同名包让用户绕过版本核对。自建源的并发构建通过写锁合并索引，先完成包和校验再原子发布索引。

应用ID稳定，卡片类型ID稳定；改名不改ID。com.ksf 命名空间受宿主保护，只接受固定公用源或内部离线资源。第三方包不得冒用官方ID，也不能宣称SHA256等价于签名认证。

应用ID统一为 `com.<发布者>.<应用名>`，规则见[清单](manifest.md)。旧两段/短ID只允许在本次登记的实例身份迁移中出现，不允许继续打包或安装；显示名称相同不代表同一应用。旧链接可定位登记的新ID，不能据此申请其他应用权限。

Core 0.3.2 的一次性配套切换使用 `runtime/tools/matched-switch.mjs inspect <实例根> <候选目录> --migrate-ids` 预演，再用 `prepare` 保存匹配Core、不可变应用包和安装索引；`apply <实例根> <switch.json回执>` 排空窗口及业务后切换，异常使用同一回执的 `recover`。先在隔离实例核验候选清单、逐文件摘要与迁移结果。工具只识别固定旧/新ID对照，不接受应用自行申报别名。副本与journal留在 `.agents/runtime-data/t15-switch/<id>/`，不自动清理。

迁移保留installationId、来源和启用状态，逐一核验并迁移user/runtime数据目录、迁移原件、后台保活、运行偏好、桌面快捷方式与卡片归属、AI任务/材料归属、通信授权/配对及操作/材料所有者。卡片实例ID、卡片配置、AI请求、消息原始清单及回执摘要不改写；未知发送操作仍先查询原operationId，不自动重发。旧收件仅通过当前安装记录的受控legacyIds关联；卸载解除关联。对已配对旧端点的发送使用迁移时登记的地址，不能失败后改地址重发。

身份迁移首次激活不把旧ID包当作新ID的previous release；旧包、索引及Core完整保留在原件和切换回执中。后续应用回退只能在新ID内按数据兼容规则进行，不能直接把单个旧目录覆盖回去。需要恢复整套迁移前实例时先停机并按回执核对完整Core、索引及宿主记录/目录副本；迁移后新业务的合并需要单独核对。本工具不自动倒退数据，也不跨设备部署。

## 运行中升级

窗口固定启动时的release；旧窗口/实际执行中的操作会使升级pending。最后窗口关闭且操作完成后，宿主统一释放旧卡片/后台、切换版本并恢复卡片配置。仅有卡片或空闲后台不会永久阻挡升级。

应用后端不要用永不结束的tasks.run来实现定时。后台定时器由startBackground和dispose管理；安装、启用及版本切换由管理器协调，不依赖浏览器继续开着。业务需在后台开始前核对持久进度，避免升级补跑重复发布。

RPC调用方超时不代表执行完成，仍在执行的动作继续阻挡不安全切换。结果未知时先查询原操作。

## 停用、卸载及回退

停用/卸载先通过当前窗口关闭保护，其他页面窗口或在途操作明确报错。卡片停止运行，保留配置、分组和几何占位；业务数据保留。重装同ID后按原记录恢复，不凭同名应用转移数据。

首次安装没有可回退版本。回退必须确有不同的previous release，并核对当前业务数据schema与旧代码兼容。回退不删除AI任务、不撤回已发布结果，也不恢复旧数据快照。

## 新 SDK v1 配套升级

宿主仅支持新契约。应用源码、清单、SDK 类型、模板及执行包一起升级，不保留旧字段映射或旧 SDK 分支。业务版本、数据 schema/revision 独立管理，业务数据及用户配置保留。设备部署先准备匹配快照、停止旧后台，再切换宿主与应用安装索引。

## SDK v1 的交付门槛

应用包内 CLI 及消息激活等新机制见[CLI 契约](cli.md)和[通信契约](communication.md)。只有实现、宿主版本/SDK 兼容检查、打包校验和[对应验收](validation.md#cli-与通信验收)完成后，才能作为可用能力发行；当前为开发实现，未正式发行 SDK 1.0.0。

CLI 实现、命令描述、文档及依赖同包交付和切换；既有执行先排空，版本条件不符时重新核对。消息消费者和持久需求的交接不得使新旧版本双消费；回退仍需核对业务数据，不因旧包存在就承诺恢复旧业务状态。已经发行的同版本包不能为补充新 CLI 或文档而覆盖。

## 初始兼容契约与迁移

清单必须声明 `minCoreVersion` 与 `dataStores`（无受管数据填[]）；schemaVersion=1、sdkVersion=1、SDK工具包=1.0.0。安装、启动和回退均核验宿主与数据。受管JSON通过prepareData显式迁移，read不执行迁移；离线检查使用 `ksf app data inspect <appId> --json`。副本不自动恢复，格式不兼容拒绝回退。完整接口及恢复规则见[后端数据](backend-data.md)与[生命周期](lifecycle.md)。

构建依赖未包含在 SDK 通用许可证中的应用，应在应用根准备 `THIRD_PARTY_NOTICES.txt`；构建器会将其附加到随包的许可证说明。KSF项目的构建脚本从锁定依赖收集 marked、DOMPurify 与 YAML 许可证，缺失时拒绝构建。该文件不是运行入口。
