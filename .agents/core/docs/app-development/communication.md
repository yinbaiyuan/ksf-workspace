# 内网通信、应用后台与工作流

状态：**SDK 3.0.0 开发实现**，2026-10-28，尚未正式发行。已实现公共通信、持久保活、消息激活和 Agent 收件；v1/v2 保持兼容。工作流仍由应用定义，示例为 `collaboration` 模板。实测范围与未完成验收分开记录。

## 运行与责任边界

KSF Web 后端保持运行时，应用可以独立于 Web 前端工作。关闭页面或浏览器不停止符合后台条件的应用；Web 后端停止后，不要求应用继续存活，不新增独立操作系统守护进程。

| 所有者 | 责任 |
| --- | --- |
| 公共通信层 | 身份、发现/寻址、在线投递、长文本/附件传输、持久接收、回执和结果查询 |
| 收件与分发 | 按端点/通道路由、保存待处理事件、应用激活、至少一次交付和接管确认 |
| 应用 | 完整业务工作流、任务组织、反馈匹配、暂停、审批、执行授权与恢复 |
| 工作台 / Agent | 通过应用公开入口推进业务；Agent 也可直接调用公共通信层 |

Core 不持有应用的步骤、分支、审批规则或通用流程定义。能力中的“协同 / Cooperation”与应用业务工作流分别存在。业务目标任务也不同于现有 `ksf task` 管理的宿主对话归档。

应用 CLI 调用及用户明确指定应用后才读取文档的顺序，见[应用 CLI](cli.md)。应用在既有消息/后台授权下处理事件，不等于远端获得本机 Agent 或审批人的身份。

## 在线投递与大内容

首版双方 KSF 后端须在线且可互访，网络管理员保障子网客户端通信和必要组播。不建设离线网络队列、代存转发、穿透或复杂网络修复。

消息使用不可变清单及多个数据部件。清单记录部件 ID、大小、类型和摘要；长文本及附件走流式传输、增量摘要和背压，不内嵌大 JSON，不经应用 IPC 整份复制。SDK、CLI 与 Agent 复用同一受控材料机制，传递材料引用而非任意本机路径。

一次逻辑投递有稳定 `messageId`，技术重试复用原 ID 和原内容；新业务消息使用新 ID。接收端完整校验全部部件并持久保存权威记录及待处理状态后，才能返回 `received`。相同 ID/内容重复提交返回原回执，不同内容明确冲突。

| 发件结果 | 含义 |
| --- | --- |
| `delivered` | 已取得与原消息、内容摘要和目标一致的持久接收回执 |
| `failed` | 已明确未提交或被拒收；初始连接失败时直接报告无法发送 |
| `unconfirmed` | 提交可能成立，回执和查询暂不能确认；保留原操作，后续显式核对 |
| `cancelled` | 已确认在提交之前终止，不能据此撤回已经收到的消息 |

上传、核对中的进度与最终结果分别展示。超时或响应丢失不证明对方未收到；结果未知时先查原操作，不能生成新 ID 盲重发。收到不代表人已读、接受任务、执行或承诺结果。

默认容量为单消息总计 1 GiB、32 个部件；清单最多 128 KiB，临时接收总额度 8 GiB，并发 4、单对端并发 2。容量配置不等于已测吞吐或长期容量承诺。连接/控制/空闲时限为 3/10/30 秒，总发送时限 15 分钟，未提交会话 30 分钟后过期。已提交消息不按暂存超时规则清理，磁盘不足或校验失败不产生接收成功回执。

## 端点与 Agent 直接通信

收发地址为 `nodeId + endpoint + channel`。`endpoint` 使用 `{kind, id}`，种类为 `app` 或 `agent`：应用端点 ID 为稳定 appId，Agent 端点 ID 为持久 mailboxId。支持应用与 Agent 的任意收发组合，不强制依赖业务应用。

```json
{
  "nodeId": "节点甲",
  "endpoint": {"kind": "agent", "id": "持久收件箱标识"},
  "channel": "team.task-feedback.v1"
}
```

节点配对/认证与本机端点授权分层。公共服务从受管应用或本机授权主体绑定来源，不信任参数自报身份；对端通过已配对节点对来源端点的声明建立信任。端点 ID 是地址，不是访问凭据；原生宿主会话 ID 不作为公开地址。

Agent 可通过公共通信 CLI 发现节点、发送材料、查询回执和主动收信，无需先调用应用。命令和完整例子见[公共通信 CLI](../cli/communication.md)。Agent 凭据保存在当前根的私有运行目录，不在标准输出中暴露；同一操作系统用户仍属于受信任边界。

Agent 收件箱由本机显式登记并授权，节点在线时可持久接收，Agent 未运行不丢原件；消费确认前可以补查。通信回执、Agent 消费确认和业务接受/执行是不同事实。自动通知或继续宿主会话需要实际适配器及授权，无适配器时仅保证可查询，不能承诺任意 Agent 被远程唤醒。

## 目标任务与反馈匹配

| 标识 | 应用应遵守的关联语义 |
| --- | --- |
| `taskId` | 首次创建目标时生成，跨节点、跨应用和多次传递保持稳定 |
| `requestId` | 一次独立协作请求及其反馈共用；独立新请求使用新 ID |
| `messageId` | 一次逻辑消息投递；重试不变，回复是另一条消息 |
| `appRunId` | 应用自己的本地工作流运行，Core 不解释内部步骤 |

推荐使用无需中心分配的随机 UUID。共同 taskId 不意味着所有节点拥有全团队完整历史；必要上下文随消息提供。任务字段属于业务载荷，通信层只处理其字节和材料，不根据任务内容启动 AI。

应用保存反馈等待时应包含运行/等待点、taskId、requestId、允许来源、反馈类型和处理游标。先保存等待，再发出请求；注册等待时补查已收到的匹配消息，覆盖反馈先到的情况。相同目标可以有多个独立请求，不能只凭 taskId 唤醒。

多个运行可以独立观察同一反馈，不默认抢占消费。等待匹配、已处理消息标记及业务状态在应用自己的事务或原子更新边界内保存。工作流已暂停时保留反馈但不绕过暂停。对方可以不接单、不执行、不反馈，不预期必然得到任务结果。

## 三种可组合的后台机制

| 机制 | 状态与契约 |
| --- | --- |
| 常驻后台 | 当前 v2 已有 `background:true` / `startBackground()`，复用现有实现 |
| 持久业务保活 | `background.retain({key, reason})` / `release(key)`，按应用范围的稳定 key 幂等登记和释放 |
| 消息激活 | 持久路由；已授权消息到达时，启动当前未运行的接收应用并交付 |

当前 `context.tasks.run()` 只是内存保活，不能充当持久工作流或恢复队列。持久保活只说明“该应用仍需运行”，不承诺外部动作可以重做。应用恢复时核对自己的业务检查点、AI 编号及消息/操作回执。

持久保活与业务文件不是天然跨文件事务：先生成稳定运行/操作 ID，取得持久保活，再发布可恢复业务记录，两者成功后才报告可靠启动。业务写入失败则释放保活；崩溃留下的空保活由应用恢复核对后清理。响应丢失时依据原操作 ID 查询，不重复创建业务。

等待反馈期间，应用保存状态并确认接收路由存在后，可以释放保活并休眠；新消息到达后再激活。首版不新增持久定时调度器，精确到时运行的业务可使用已有常驻后台机制。

同一应用的数据和消息消费只有一个后台所有者。前端打开、Agent 调用或多条消息同时到达时复用它；用户停用、卸载、明确禁止后台或暂停业务，不能被远端消息绕过。Web 后端重启后只恢复本机持久需求和待处理消息，不声称停机期间仍可收信。

## 消息路由与接管

应用在包中声明消息通道，安装/授权后平台保存路由，不依赖应用进程常驻维持 JS 回调。以下为 SDK v3 Manifest 片段，完整应用还必须声明后端及 `messages.receive` 权限：

```json
{
  "schemaVersion": 2,
  "sdkVersion": 3,
  "activation": {
    "messages": {
      "channels": ["team.task-transfer.v1", "team.task-feedback.v1"]
    }
  }
}
```

声明不自动取得接收/激活许可。本机另保存通道、允许来源及是否允许激活；准备和提交都检查端点仍受支持、已启用且被授权。未知目标、停用应用或未允许的通道拒收，不自动安装应用。Agent 端点单独登记，不依赖应用 Manifest。

应用端点的可靠顺序是：

1. 完整消息与初始 `pending` 投递状态一起发布，之后才返回网络回执。
2. 分发器互斥启动/复用应用并持有临时投递租约。
3. 调用 `onMessage(event)`，传入事件/消息 ID、认证来源、通道和材料引用。
4. 应用校验并持久接管事件，将去重标记与业务变更一起保存；需继续长业务时先取得持久保活再发布可恢复记录，然后返回确认。
5. 平台记录 `acknowledged` 并释放临时租约；后续长业务另取持久保活。

`onMessage` 需有界返回，不等待整个工作流完成。交付按至少一次设计；保存成功但确认丢失时可重投，应用必须去重。超时而原调用可能仍继续时，先核对或等待原进程退出，不能并发重投同一处理。

投递诊断区分 `pending`、`delivering`、`acknowledged`、`parked` 和 `suspended`。连续失败 5 次后保留消息并停放，有限退避上限 60 秒；它是本地处理重试，不是离线网络补发。业务拒绝可持久记录后确认接管；如需告诉对方，另发业务消息，不能改变原接收回执。

## 数据、升级与验收

公共消息/材料、回执、端点、投递和保活记录由各自公共域持久保存；工作流、等待、审批和业务去重记录归应用 dataDirectory。索引可重建，已提交材料不能被临时缓存清理误删。应用升级时协调检查点和消费者交接，不让新旧版本同时消费；回退不自动回退业务数据。

工作台和应用 CLI 使用同一公开业务操作、稳定操作 ID 和版本条件，审批绑定相应材料版本。是否执行 AI 或工具由接收端授权规则及应用决定，收到消息不能直接映射为任意本机方法调用。

验收须覆盖前端关闭、消息激活、大材料完整性、回执丢失、重复/乱序反馈、崩溃恢复、停用及升级交接。详细检查见[CLI 与通信验收](validation.md#cli-与通信验收)。本文是开发接口契约；具体通过范围以测试记录为准。

## SDK v3 调用

后端使用 `ApplicationBackendContext3`：`context.messages.registerFile({path,name,mediaType})` 登记本应用 dataDirectory 内的普通文件，返回 materialId；`send({operationId,to,channel,payloadPartId,parts})` 异步返回操作；`status/reconcile/cancel(operationId)` 查询、对账或取消。发送必须预先生成稳定 UUID operationId，重试保留相同材料引用和参数。

接收端用 `inbox({after,limit})` 补查，`read(messageId)` 取得清单，`readPart(messageId,partId)` 取得受管材料路径和元数据。游标是单调接收序号，不按随机消息 ID 排序。`onMessage` 返回成功即表示应用已持久接管；业务需要拒绝也应保存自己的处理结果后返回。

前端从 `@ksf/sdk/communication` 创建 `createMessageMaterialClient(sdk)`，通过 `upload(blob,name,signal)` 和 `read(messageId,partId,signal)` 流式上传/读取；业务指令仍用 sdk.call。材料不会通过普通 1 MiB RPC 整份搬运。

大文件下载可将 `downloadURL(messageId,partId)` 返回的应用范围相对 URL 赋给下载链接，由浏览器处理流式响应；无需先聚合为 Blob。该 URL 不含令牌，但仍依赖本机有效应用实例和接收权限，不是可分享的公开下载地址。

权限：发送、登记、查询发送与节点列表需要 messages.send；收件和材料读取需要 messages.receive；持久保活需要 background。应用清单声明、节点信任、通道来源和消息激活授权分别核对。设置界面位于“系统设置 → 内网通信”。

`context.peers.list()` 返回 `paired`、`discovered` 和可选的 `local` 只读状态；local 包含公开设备身份、是否启用、发现开关、实际监听地址、消息容量与发现错误。它不包含设备私钥、Agent 令牌或管理凭据，也不允许应用自行配对、变更来源授权或修改监听。旧调用方仍可只读取节点列表；兼容旧开发宿主时应允许 local 缺省。

暂存发送材料另受同值总额度约束。登记以流处理，逐块限制总大小；超过额度返回 COMM_QUOTA_EXCEEDED。材料登记后 30 分钟可回收，正在 preparing/sending 的操作保留引用；已接收消息材料不走这项暂存清理。业务长期正文和结果应保存在应用自己的 dataDirectory，不能把临时 materialId 当长期文件库。

部件 partId 以英文字母或数字开头，其余只使用英文、数字、点、横线和下划线，最长 128 字符。为跨平台一致性，不允许冒号、Windows 保留名称或仅大小写不同的重复部件 ID；payloadPartId 必须精确引用一个部件。节点证书主体按公钥标识唯一命名，配对仍核对完整证书指纹与 nodeId。
