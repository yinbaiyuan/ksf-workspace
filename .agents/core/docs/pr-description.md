# PR 说明规则

本规则用于向 KSF Core 提交 PR 时的标题与正文，也可供普通系统仓库贡献使用。PR 说明应让未参加原讨论的审阅者理解问题、最终行为、验证依据和兼容影响。Git 提交信息遵循[提交信息规则](git-commit-message.md)，公开范围与授权仍遵循[Git 协作规则](git.md)。

## 标题与范围

标题沿用 D01 的 `type(scope)[!]: 中文动作摘要`、类型、范围和长度规则：建议不超过 50 个 Unicode 码点，硬上限 72，末尾不加句末标点，避免泛化摘要。默认与贡献生成的 Core 提交标题一致；当前贡献接口使用一个共同标题，没有单独的 PR 标题覆盖参数。

一个 PR 围绕一个可独立解释的目的，说明整个选定差异最终产生的结果；无关目的先拆分。Markdown 中的运行定义按实际行为选择类型，不仅根据文件扩展名判断为 docs。

## 四项必填正文

正文为 Markdown，首先按顺序包含以下四个二级标题，每项恰好一次，内容非空。小改动可以每项一句，不要求最低字数。

| 标题 | 要说明的内容 |
| --- | --- |
| `## 背景与目的` | 原有问题、具体触发情境，以及希望达到的行为；必要时用修改前后的例子说明 |
| `## 主要变更` | 最终实现的行为变化、理解方案所必需的取舍；不逐个罗列文件或复制代码 |
| `## 验证结果` | 实际命令或检查、结果、覆盖范围和未验证部分；未执行须说明原因 |
| `## 影响与兼容` | 受影响的调用、对象、持久数据或运行行为；旧用法是否有效、是否需要迁移 |

四项之后可按需增加 `## 迁移与回滚`、`## 审阅重点`、`## 关联信息`、`## 剩余工作`，各最多一次。无需求直接省略。其他细分内容用段落、列表或三级标题表达，避免制造另一套二级章节名称。

破坏性变更使用标题 `!`，且必须有非空的“迁移与回滚”，说明旧用法、替代方式、迁移要求及可行的回退边界；没有安全回退时明确原因。Git 消息仍需其自身的 `BREAKING CHANGE:` 尾注。涉及持久数据的改动，即使不破坏兼容，也要说明旧数据的读取、保留、转换或恢复方式；程序不能只根据标题判断所有数据影响。

关联信息只填写真实可访问的 Issue、设计或证据链接。使用会在合并后关闭 Issue 的关键字前，核对目标问题与本次范围。审阅者无法访问本机路径或私人项目记录，正文应自含必要背景，公开链接仅作补充；不公开个人资料、凭据、私人路径、本地任务编号或个人提交历史。

## 依据与生成过程

1. 以实际选定差异为边界。Core 贡献读取已提交 HEAD 与其保存的正式 Core 基线，不拿未提交工作、私人提交说明或未来计划代替当前变更。
2. 核对已确认需求、差异的必要上下文、当前定义和实际验证记录，形成共同事实。原因不靠文件名猜测，兼容性不能无依据写“无影响”。
3. 分别生成 Git 消息和 PR 正文。Git 使用原因、变更、验证；PR 使用本规则的四项结构。可以复用已核实的事实，不将两份正文强制写成同一文本。
4. 对照最终差异自审：覆盖范围完整，关键取舍有解释，已放弃方案不混入现行行为。测试计划、历史测试、人工推演、同一 Agent 走查与实际程序测试分开说明；有测试文件不等于测试通过。
5. 格式校验后再核对事实、验证适用性和公开范围。审阅期间若实际范围变化，重新整理标题、正文及对应验证；需要新的贡献内容时重新准备并审阅。

稳定生成指事实边界、结构与判断依据一致，不要求每次措辞逐字相同，也不由程序编造动机或测试结论。

## 模板与检查

使用[正文模板](templates/pr-description.md)，替换占位内容，删除无需求的模板提示。标题单独提供，正文不重复添加一级标题。示例仅演示格式，不声明实际实现或验证：

```markdown
## 背景与目的
对象设计方法未要求说明持久字段如何影响实际工作，设计结果容易只列设置而未采用。

## 主要变更
- 设计时评估持久需求，按需定义字段、消费行为和维护时机。
- 让三项设计基本功共用字段模板与使用方法。

## 验证结果
- 未执行：本段仅演示 PR 说明格式，不代表实际提交或测试结果。

## 影响与兼容
影响后续对象设计方法；不改变现有 user-data 存储格式，也不初始化个人记录。
```

```sh
.agents/ksf pr-description template
.agents/ksf pr-description check --title 'feat(objects): 支持设计对象持久设置' --from /tmp/pr-description.md --json
```

[检查命令](cli/pr-description.md)只验证标题、章节及顺序、内容非空、明显占位符、控制字符、大小和破坏性迁移章节。HTML 注释、围栏代码中的模板标题不能充当必填正文，代码示例需有实际说明文字。检查始终返回 semanticReviewRequired:true；它不证明变更完整、测试真实、兼容性结论正确或所有私人信息都已识别。

## 贡献计划与发布

`contribute prepare` 保留 `--body/--body-file` 作为 Git 正文，另外要求 `--pr-body/--pr-body-file` 二选一作为 PR 正文；参数及文件说明见[contribute](cli/contribute.md)。缺少独立 PR 输入不自动套用 Git 正文。标题与两份正文的格式在读取 Git 或网络前检查，随后取得正式基线，将来源说明加入完整 PR 正文。

新计划 schema 4 保存共同 title、Git body、完整 commitMessage、规范化的 PR 主体 prDescription，以及含自动来源说明的完整 prBody；这些全部纳入 digest。prepare、read 与 submit dry-run 都能展示实际发布文本。submit 创建提交与草稿 PR 时使用各自冻结文本，不在发布阶段临时追加内容。生成来源只包括正式 Core 版本、原版提交及选定系统差异说明，不公开实例本地 sourceCommit。

首次发布前修改标题、正文或 HEAD 需重新准备和审阅。创建后 PR 说明可在用户授权下通过正常托管工具随评审补充，冻结的 Git 提交及本地贡献计划保持原样。普通重试只核对 PR 身份、目标、提交和状态，不覆盖已编辑的远程标题或正文；这不表示远程文字仍与最初审阅文本一致。准备送审时重新核对当前说明和差异，草稿转 Ready for review 按用户请求执行。

旧 schema 1／2／3 计划保持可读，不在旧 digest 下补造 PR 文本。没有已有发布记录时重新 prepare；有已有记录时只能只读核对既有 PR，不能创建远程对象或改写旧记录。schema 3 的冻结提交消息仍须核对。重复内容识别、部分成功恢复及未明状态保护继续适用。

## 参考

本规则参考 [Google 变更说明指南](https://google.github.io/eng-practices/review/developer/cl-descriptions.html)对变更内容、原因、取舍和最终说明更新的要求，以及 [GitHub PR 评审建议](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/getting-started/best-practices-for-pull-requests)对聚焦范围、上下文、审阅指引和自审的建议。固定四项、中文标题与独立正文校验为 KSF 自身约定，不是托管平台强制模板。
