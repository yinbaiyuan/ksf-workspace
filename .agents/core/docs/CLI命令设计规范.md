# CLI 命令设计规范

## 地位与适用范围

本文件是 KSF 后续 CLI 命令设计的统一依据，规定命令结构、命名、操作语义、参数、输入输出、错误及文档要求。各命令的具体职责和业务规则在 [CLI 命令文档目录](cli/index.md) 下维护，不复制另一套公共规范。

规范约束后续设计与实现，不代表文中接口已经可执行。已实现行为以[当前 CLI 能力说明](cli/overview.md)、源码和测试为准。规范更新不自动表示其中的全部设计词汇已成为可调用参数。

## 一、命令结构与职责

标准结构：

```text
ksf <命令> <操作> [目标] [选项]
```

| 要素 | 表达什么 | 示例 |
| --- | --- | --- |
| 程序入口 | 使用哪个工具 | `ksf` |
| 顶级命令 | 管理哪个对象或能力领域 | `metadata`、`partner`、`cooperation` |
| 操作 | 对该领域做什么 | `read`、`write`、`remove`、`check` |
| 目标参数 | 操作哪个明确目标 | 文件路径或对象引用 |
| 选项 | 输入来源、范围或输出方式 | `--fields title`、`--from data.json`、`--json` |

对象或能力领域使用独立顶级命令，共用操作保持相同含义。跨对象组合用例可以有独立入口，例如 `context capabilities`；内部复用对象服务，不复制扫描与解析逻辑。

一个命令只有单一明确动作时，不强加操作层。现有 `hello`、`build`、`test` 可以直接调用；`context capabilities` 使用能力领域与操作两层；`runtime verify` 保留已有结构。默认不超过“命令＋操作”两层，新增层级必须说明独立职责。

不为形式完整强制每个命令实现完整 CRUD。通用元数据工具管理任意 Markdown 的 frontmatter；对象服务另行应用[对象元数据规范](对象元数据规范.md)及类型业务规则。

## 二、命名要求

- 命令、操作、长选项使用英文小写，多词用连字符连接，例如 `data-package`、`--dry-run`。不使用下划线、驼峰或随意缩写。
- 对象命令优先使用单数名词，例如 `partner`、`cooperation`、`competency`；集合操作通过 `list` 表达，不再增加复数命令。
- 操作使用常用动词，名称描述用户意图，不暴露内部实现步骤。
- 同一含义只保留一个标准名称。新的通用读取使用 `read`，不并设 `get/show/read`；通用检查使用 `check`，不并设 `check/validate`。
- `init/set/patch` 不作为通用写入的平行入口；只有存在无法用统一操作表达的独立业务目的，才设计新的操作并说明差异。
- 默认只提供长选项，保留 `-h` 作为 `--help` 的常用形式；其他短别名须有明确使用价值，不自动生成首字母别名。
- 文档标题及解释可以使用中文。用户字段名、显示名称、路径和值不受 CLI 英文命名规则限制。
- 已存在的命令不因本规范静默改名；兼容或迁移需单独设计。

## 三、操作词汇与能力边界

| 操作 | 标准含义 | 约束 |
| --- | --- | --- |
| `list` | 列出范围内对象或条目及摘要 | 不默认返回全部正文；有分页或截断必须明确告知 |
| `read` | 读取明确目标的内容或字段 | 不修改目标；字段缺失与显式 null 分开表达 |
| `write` | 写入提供的数据 | 明确创建与更新条件、合并或替换范围，不默认覆盖未指定内容 |
| `remove` | 移除明确指定的内容 | 必须给出删除范围，不以省略范围代表全部删除 |
| `check` | 检查并报告问题 | 默认不修复、不修改目标，明确覆盖的规则与未检查部分 |

通用元数据写入统一为 `write`：frontmatter 不存在时添加，已存在时更新提供的顶层字段，未提供字段保留。字段值整体替换，不隐式深度合并；写入 null 是赋值，不是删除。该规则不自动授予对象层创建对象、转换状态或更新引用的能力。

读取、修改和检查同一领域不重复定义字段语义。对象层若需要独立的创建、迁移或发布操作，应以真实业务边界为依据，不能把简单的单字段与多字段差异拆成不同命令。

## 四、参数与选项

### 位置参数

主要目标优先使用一个位置参数。每个命令必须说明它接受文件路径、目录、对象 ID 还是其他引用，不靠猜测在不同类型之间切换。

新命令的普通文件参数及 --from 输入文件，相对路径统一按启动入口定位的 KSF 根目录解析，不随调用者当前工作目录改变；绝对路径直接使用。系统资产也按该 KSF 根定位。对象 ID 的查找范围由对象命令另行定义，不把 ID 当路径处理。已有命令未提供的路径参数不因规范更新自动出现。

路径可以包含空格或中文，示例应展示必要的 shell 引号。参数解析器应支持 `--` 结束选项，便于传入以连字符开头的目标。命令位置不变，操作后的选项原则上不依赖排列顺序。

### 通用选项

| 选项 | 统一含义 | 适用要求 |
| --- | --- | --- |
| `--fields <名称...>` | 指定一个或多个字段 | 选项只出现一次，后接空格分隔的字段名；每项按完整名称解释，不按逗号拆分 |
| `--data <JSON>` | 内联结构化输入 | 与 `--from` 互斥；解析为数据，不执行表达式 |
| `--from <文件>` | 从文件读取结构化输入 | 与 `--data` 的数据格式和操作语义一致；格式须明确 |
| `--all` | 显式选择当前目标中的全部相关内容 | 必须说明“全部”的边界；与同一层级的局部选择互斥 |
| `--source <来源>` | 选择对象解析来源 | 明确默认优先级、显式来源不回退、all 是否适用；对象读取默认 effective |
| `--part <部分>` | 选择读取内容类别 | 对象 read 使用 metadata/body/all，默认 all；未选内容字段不输出，不隐式展开资源 |
| `--json` | 结构化输出 | 只改变输出格式，不改变业务动作 |
| `--dry-run` | 预览修改及检查结果 | 修改类操作提供；不写入业务目标，不触发不可逆业务动作 |
| `--help`、`-h` | 查看当前命令或操作的帮助 | 后续新命令应提供对应层级帮助 |

通用选项是统一词汇，不是所有操作自动接受的全局参数。每个操作只声明实际支持的选项。参数缺值、未知参数、互斥参数或不允许的重复选项必须报错，不忽略、不偷偷采用最后一个值。

可重复选项必须明确声明。`--fields` 是单次出现的多值选项，后面至少提供一个字段名；字段名以空格分隔，重复字段按首次出现顺序去重。名称包含空格时使用 shell 引号；遇到下一个选项或选项结束符 `--` 时结束字段列表。单字段和多字段使用同一语法：

```sh
ksf metadata read note.md --fields title
ksf metadata read note.md --fields title tags --json
ksf metadata read note.md --fields "display name" tags
ksf metadata remove note.md --fields obsolete draft
ksf metadata remove note.md --all
```

上述 remove 的 `--all` 仅移除该文件的元数据块，保留 Markdown 文件与正文。`--all` 和 `--fields` 不能同时出现；remove 未指定二者之一时报参数错误。read 未指定字段时读取全部元数据。

不默认增加能绕过校验的 `--force`，也不要求每个命令都增加确认参数。程序参数不能替代宿主权限和用户授权。

### 每个参数必须记录的信息

名称、位置或选项类型、值类型、是否必填、默认行为、是否可重复、单次接受的值数量、允许值或格式、互斥和依赖关系、作用范围。路径参数还要说明解析基准；选择参数要说明未命中、多项命中和顺序规则。

## 五、输入与批量处理

- 结构化输入使用 JSON 时，保留字符串、数字、布尔值、null、列表和映射的类型，不把所有值转换成字符串。字段映射输入的顶层必须是对象。
- `--data` 与 `--from` 只改变输入来源，不改变更新逻辑。标准输入只有在命令明确设计后才支持，不能默认为缺少输入时阻塞等待。
- 元数据首版按顶层完整字段名选择；含点号的字段名不自动解释为嵌套路径。嵌套映射与列表作为字段值整体处理。
- 多字段删除与更新作为一次逻辑操作，整体检查后一次写入。删除不存在的元数据字段不报错，结果区分已删除与原本不存在。
- 单目标的多字段操作不等于多文件事务。跨文件或多对象批量操作必须单独说明原子性、失败后是否继续及逐项结果，不凭一个汇总成功标记掩盖部分失败。
- 原始 YAML 损坏时不得通过写操作静默重建并丢弃原内容；修复工具需要另行设计。
- 对象 write 输入为 metadata 映射与 body 字符串的信封，省略部分保留，元数据顶层合并；metadata write 的输入直接是字段映射，两者不能混淆。
- 四类能力对象以完整承载目录管理。普通 write 只写用户区，首次系统派生包含全部资源和基线；remove 删除整个用户目录，归档则通过 write 明确改变 status。对象身份、版本、修订与基线规则只在公共元数据规范和对象命令公共规则维护。

## 六、输出、结果字段与错误

默认输出面向人阅读，`--json` 面向 Agent 和程序解析。两者表达同一结果。一次普通 JSON 调用输出一个完整 JSON 值，不夹杂日志；若要设计流式协议，必须另行声明。

新增命令的 JSON 业务结果统一包含以下字段；具体业务结果嵌入 data，不将不同命令的内容字段强行统一：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `ok` | boolean | 本次声明的操作是否成功完成；部分失败为 false |
| `command` | string | 顶级命令名，例如 metadata |
| `operation` | string 或 null | 操作名；单动作命令为 null |
| `data` | object 或 null | 业务数据、检查发现、逐项结果、变更或预览信息 |
| `errors` | array | 失败项；无错误时为空列表 |

错误项至少包含稳定的 `code` 和可读的 `message`，按需附上 `target`、`field` 等定位字段。错误码使用英文大写加下划线，不要求调用方解析自然语言文字。

读取集合的完整性、字段是否存在、是否实际产生变更和是否只是预览，分别由对应命令在 data 中明确定义；不把这些含义全部塞进 ok。未设置、空集合、字段不存在、值为 null、读取失败必须按业务语义区分。

业务结果（包括可用的部分结果与错误集合）写入 stdout；运行日志和启动层诊断写入 stderr。新增命令在进入业务处理器后，应尽量对成功和失败都返回统一 JSON 结构；启动层尚未进入处理器时可能只有 stderr 文本，调用方必须同时检查退出码和输出，不能无条件解析 stdout。

| 退出码 | 统一含义 |
| --- | --- |
| `0` | 操作成功；允许有明确记录的无变化或未设置结果 |
| `1` | 执行失败、检查发现不合格或部分失败 |
| `2` | 命令、参数或输入调用格式错误 |

缺少数据选项、JSON 输入无法解析、未知参数属于调用错误；目标 Markdown 损坏、文件不可读或并发冲突属于操作失败。更具体的错误码在命令文档定义。信号终止与外部测试运行器退出状态按实际结果报告。

现有命令已经采用的 command 字段形式、单个 error、JSON 错误输出位置和返回字段保持现状，不因新规范改变。新增接口采用本节结构；已有接口若迁移，需要明确兼容范围与测试。

## 七、读写与程序架构

- CLI 层只负责命令适配；业务服务可由其他接口直接调用，不通过 CLI 子进程复用内部功能。
- 通用格式处理、对象规则和业务组合相互分离。metadata 不硬编码对象字段；对象操作在保存前执行自身约束；context 组合对象服务，忠实组织其数据，不重复实现覆盖规则或生成业务摘要。
- 命令文档明确自身副作用，包括目标、临时文件、缓存和派生产物。只读或预览不能冒充对整个启动流程零写入的承诺，现有 bootstrap 可能准备本机运行时。
- 修改类操作在发布前完成必要检查，保留未授权范围和未修改内容。单文件更新采用适当的原子写入机制，并检查并发修改。
- 原子替换不等于并发隔离；锁、版本比较或其他协调方式、冲突处理及失败清理需要在实现设计中明确。
- 重复执行是否无变化、是否可以安全重试，需要逐操作说明。不得因一次调用结果不明就重复不可逆动作。

## 八、命令文档必备内容

每个顶级命令在 `docs/cli/<命令名>.md` 中维护一份说明，并从索引链接。至少包含：

1. **状态与职责**：设计中还是已实现，解决什么问题，不承担什么。
2. **调用结构与操作表**：命令、操作、目标类型及每项行为。
3. **参数表**：按本规范要求列出类型、默认、重复、互斥与依赖规则。
4. **输入与输出**：输入来源、数据结构、文本及 JSON 例子、关键结果字段。
5. **异常行为**：缺失、无匹配、损坏、冲突、部分失败、错误码和退出码。
6. **文件影响**：读写范围、预览、批量原子性、并发及重试行为。
7. **实现与验证**：模块职责、源码与测试入口、实际验证范围或待实现事项。

设计中的文档可以保留明确待定项；进入实现前必须收敛会影响接口、写入边界与验收的事项。已实现命令的帮助只列出真实支持的操作，不能因已有设计文档就加入可执行帮助。

说明文档用中文，命令和字段用标准名称。不要在多个文件重复维护同一公共规则，命令文档通过引用继承本规范，只补具体行为与合理例外。

## 九、验收与现有文档衔接

后续实现应覆盖正常输入、缺失和错误参数、重复及互斥选项、单项与多项、空值与缺失、JSON 和文本输出、退出码，以及实际存在的文件副作用。修改类操作另验证预览、失败不部分写入、并发冲突和正文或非目标内容保留。

本次将未实现设计中的 show/validate 统一为 read/check，将 metadata 的旧六操作收敛为 read/write/remove/check；旧草案不是兼容接口，不保留重复别名。

现有 hello、runtime verify、build、test 和帮助行为不变。对象类型、状态、版本、引用等业务规则继续在对应规范中收敛，不由 CLI 命名标准代替。
