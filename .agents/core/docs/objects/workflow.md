# 工作流 Workflow

工作流承载一类业务中多个搭档的协同机制。它把分散的责任连接起来，使各搭档的局部结果能够组成满足整体目标的交付。

## 解决的问题

当不同专业责任之间存在依赖、交接、协调或返工需求时，仅定义各搭档“各自做好什么”还不够。工作流说明谁先提供什么、谁接手、什么条件下可以继续，以及出现分歧或失败时怎样推进。

普通业务工作流的成立条件是多个独立责任确实需要协同。步骤多、材料多、处理时间长或问题复杂，都不能单独构成创建理由。

## 持有的内容

- 业务目标、适用情境、必要输入和整体交付。
- 参与搭档、各自分工、责任边界与协调责任。
- 阶段依赖、先后关系及允许并行的条件。
- 交接的输入、输出、接受条件和未满足时的处理。
- 分歧协调、异常、返工、范围变化及中止方式。
- 整体完成条件，以及如何确认各部分已形成有效交付。

阶段和顺序服务于协同，不为流程完整强加所有阶段。工作流可以有条件分支、循环和提前结束，不必是一条固定直线。

## 与搭档、基本功的边界

工作流判断跨责任的协作安排；搭档负责自己承担的业务；基本功持有专业处理的方法与质量标准。

例如，“需求定义未满足交接条件时返回产品搭档”属于工作流；“产品搭档负责澄清需求并跟进待决项”属于搭档；“怎样判断需求是否清晰、完整和有依据”属于基本功。交接可以引用专业质量标准，不应另写一套冲突标准。

一个搭档内部也可以分阶段、追问、循环和检查。这些步骤只服务其自身责任时，保留在搭档或相应基本功中。不要为了建立工作流而把一个完整责任人为拆成多个搭档。

多个搭档表示多个责任角色，不表示已经创建多个真实 Agent。一个 Agent 可以按约定承担多个角色，实际是否并行运行需由执行环境和授权决定。

## 何时建立或复用

先检查是否已有适用的协同机制。只改变本次人员安排、输入材料或进度时，通常记录到项目；同一类业务出现稳定的新协同需要，才考虑完善或新建工作流。

**示例情境**：功能交付需要产品搭档明确需求、研发搭档实现、验证搭档检查结果。需求变化影响实现和验收，需要约定交接、回退与整体交付，适合用工作流承载。

**反例情境**：知识整理搭档读取数百篇材料，经过筛选、萃取和复核完成交付。仅凭材料量和内部步骤，没有必要新建工作流。

## 定义与运行

入口文件为 `workflow.md`，以承载目录整体管理。已实现 list/read/write/remove/check，公共管理规则见[对象命令](../cli/objects.md)。

系统区为 `.agents/core/abilities/workflows/`，用户区为 `能力/工作流/`。工作流摘要参加初始能力发现，命中候选后再读取完整定义；运行时优先匹配适用工作流，不强行套用。

[根 AGENTS.md](../../../../AGENTS.md)是整个 KSF 的特殊入口工作流。它属于已约定的系统入口机制，不作为普通业务工作流可以只承担单一责任的依据。

定义方法见[工作流设计基本功](../../abilities/competencies/workflow-design/competency.md)，公共字段见[对象元数据规范](../对象元数据规范.md)。定义文件不等于一次实际运行，具体执行的进度、产物和证据由相应项目或任务记录承载。
