# 项目 Project

项目承载一件具体事情的目标、现实情境、推进过程和成果。它使人和 Agent 能够理解这件事为什么做、做到哪里、哪些决定仍有效，以及下一步需要处理什么。

## 解决的问题

可复用能力不能代替本次工作的真实上下文。同一个搭档和基本功服务不同项目时，用户目标、约束、材料、决定和完成条件可能不同。项目保存这些与具体事情相关的事实，避免把临时情况写成通用规则。

这里的项目可以是开发、研究、生活安排或学习目标，不限定为软件仓库。它是工作资产的承载概念，不是新增的初始能力路由候选。

## 持有的内容

- 本项目的目标、范围、背景、约束和完成条件。
- 已确认事实、关键输入、材料及原始来源入口。
- 决策、取舍、待决问题和必要的讨论依据。
- 当前成果、进展、未完成事项和后续安排。
- 实际采用的能力、处理结果、验证证据与实践记录。

记录应区分计划与实际、候选与采用、推测与证据。不把写出计划当成执行完成，也不把一次结果概括成已经成立的通用规律。

## 与工作流的区别

工作流定义可复用的多搭档协同机制，项目记录某件具体事情的现实情况。项目可以使用一个工作流，也可以由一个搭档直接承接，还可以在不同任务段采用不同安排。

例如，“功能交付中的需求—实现—验证协同”属于工作流；“本次登录功能的范围、接口决定、测试结果和交付进度”属于项目。

本项目的临时任务顺序可以直接记录，不必先提炼工作流。只有具有复用价值且确有多个独立责任需要协同，才考虑形成长期工作流。

## 与知识、能力的区别

项目记录“这次发生了什么、为什么这样决定”。跨项目仍有理解价值的解释和认识，可以提炼到知识；值得复用的专业方法可以进入基本功；稳定的协同经验可以进入工作流。

提炼时保留来源和适用条件，项目中的原始证据仍留在其来源位置。新知识或新能力应说明概括依据，不能让提炼结果反过来改写已经发生的事实。

本项目选择了某个标准，不代表所有项目都必须采用。需要改变可复用能力时，按该对象的设计和变更范围处理，不能只因项目记录中出现了新做法就自动生效。

## 何时创建与维护

**示例情境**：某项产品迭代需要持续保存目标、输入、取舍、阶段成果与验收证据，适合由项目承载。

**反例情境**：只是记录一条可独立理解的领域认识，通常直接进入知识；只是封装一种可重复执行的方法，通常进入能力。

一次简单请求不必自动创建项目。已有项目可以承接时，优先回到原项目，避免重复保存同一事实和进度。

## 存储与实现边界

KSF 内的项目入口位于 `项目/`。实际工作文件可以位于外部 Git 仓库或其他工作区；项目保存足以理解和继续工作的上下文与引用，不要求把代码、附件和成果全部复制回来。

最小稳定入口采用 `项目/<项目名>/project.md`，由普通 Markdown 保存上述必要内容；没有能力对象 ID、版本或 user_revision 的必填要求。名称和摘要可以使用已有元数据，没有时从标题与正文取得，不伪造缺失事实。已有领域资料通过根卡链接按需读取，不要求首版建立递归树或自动拆分机制。

归属发现、继续任务、工程关联和读取方法由 [project-route](../../abilities/competencies/project-route/competency.md)持有；已授权写回由 [asset-maintenance](../../abilities/competencies/asset-maintenance/competency.md)处理。[project CLI](../cli/project.md)已提供 list/read/write/remove/check；项目正文与资料也可用宿主工具作已授权的局部编辑，通用 metadata CLI 仍可管理元数据。项目归属的语义判断由 Agent 完成，没有持久化自动绑定服务，项目不套用能力对象的 ID、版本与派生制度。
