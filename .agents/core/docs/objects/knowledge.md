# 知识 Knowledge

知识承载可以被理解、解释、检验和修订的认知内容。它保存事实、概念、解释、观点与经验认识，以及这些内容的依据和适用条件。

知识主要由人沉淀：人决定内容、认识、采纳与修订，按需要使用能力工具辅助归纳、提炼、比较和总结；KSF 根据已有框架辅助确定记录位置，完成已授权的保存、关联、导航维护与核验。

## 解决的问题

人和 AI 都需要知道某个判断为何成立、哪些情境下不成立、证据来自哪里。知识使这种理解可以被反复阅读、讨论、组合和更新，而不依附于某一次任务或某一个搭档。

知识不是能力尚未成形时的临时存放区，也不只是原始材料仓库。它可以长期作为有独立价值的认知存在；原始资料则通过来源关系支持理解与核对。

## 适合承载的内容

- 有适用范围与来源的事实、概念、定义和领域关系。
- 对现象的解释、因果假设、模型与观点。
- 从案例中形成的认识、经验分析、反例与限制。
- 对方法论的解释：为什么有效、依赖什么条件、有哪些争议。
- 支持或反驳上述认识的证据，以及仍待确认的问题。

具体知识不必机械填满这些类别，但应让读者区分事实、他人主张、作者推断和候选认识。形成一篇文档不代表其中判断已经验证。

## 与能力的本质区别

知识保存“理解什么及其依据”；能力规定“承担什么责任、如何处理、怎样协同与执行”。两者都能指导行动，也都可以供 AI 使用，区别在内容的主要责任。

以产品设计为例：

| 内容 | 主要归属 |
| --- | --- |
| 用户常把想到的解决方案表达为需求；这一现象的解释、案例与限制 | 知识 |
| 需求澄清时区分目标与方案，缺少关键情境先追问，结果应满足明确标准 | 基本功 |
| 持续承接用户的产品问题，组织分析并推进到可交付的需求结果 | 搭档 |
| 产品、研发、验证搭档之间的交接与返工机制 | 协同 |
| 某位用户本次提出什么、团队最终采用什么方案 | 项目 |

“方法论”不是一个自动指向能力目录的标签。讲清一种方法的原理与认识，可以是知识；把它确立为反复采用的专业处理约定，则由基本功持有相应方法与标准。

## 怎样避免重复沉淀

同一材料含有多个层面的内容时，先判断主要归属，保留关联，不整篇复制。完整的混合材料可以整体主存，其他分区引用；内容本来独立或用户明确要求拆分时再分别记录：

1. 判断哪些内容是项目中的特定事实，哪些认识可脱离该项目独立理解。
2. 判断哪些内容只是解释或经验，哪些已经形成希望采用的处理方法与标准。
3. 独立有价值的解释保留在知识中；现行专业方法在基本功中维护；两者通过引用连接。
4. 如果整份材料本来就是完整的专业方法，可直接沉淀为基本功，无需先制作知识副本。

反过来，一条认识即使很成熟、很有用，也不必转成基本功。只有需要把它组织为某类专业处理时，才产生这种设计需求。

## 与数据包、项目的边界

知识以认知主题和问题组织理解；数据包以使用情境组织一组资料。知识可以被多个数据包或基本功引用，其主要内容仍在一处维护。让 AI 读取知识，不以先包装数据包为前提。

项目保存具体事情的事实、进展和决定；知识保存可独立讨论的认识。项目案例可以支撑知识，但应保留当时的情境，不把个别结果无条件推广。

新的实践可能支持、限制或推翻原有认识。更新知识时说明证据与影响；如果基本功依赖这条认识，还需检查方法是否应修订，不把知识文件更新等同于所有能力已经同步更新。

## 何时沉淀与存储

“放哪里合适”只提供位置建议；“记下来”按内容性质和本次目的确定位置后保存；“处理后保存”先由适用能力完成用户要求的内容处理，再按同一有效授权记录。默认保留用户原文或其指定结果的含义，标题、段落和链接可按需整理；归纳、语义改写、结论合并和删减按明确要求进行。

未验证的个人认识可以保存，保留其原有不确定性，来源未知如实说明，不要求先验证或完成全部模板。新内容与旧认识冲突时说明差异并建议补充、并列或替换；用户已明确修订目标和内容时直接执行，不额外要求采纳审批。没有修订意图时保留现状，不按新材料日期自动改写旧结论。

记录和修订优先复用已有正文，写前核对最新基线，保留既有有效内容与来源原件；并发变化停止受影响写入，重复无差异不重写。沿用已有修订约定，不新增强制版本字段或逐条日志。导航仅维护必要概述、入口和过时占位，详细内容留在正文。系统不自动发现沉淀价值、采纳认识或修订结论；短期记忆转长期资产另行设计。

原始材料随所支撑的目标保存，默认放在目标目录的 `资料/` 子目录；已有附属资料目录保持原位，不另建根级“源档”。正文保留来源、来源日期和原件入口，区分原始信息与从中形成的认识。一份原件有一个主归属，其他知识、方法论、项目或用户能力通过链接引用。

例如，会议记录支撑“需求澄清”方法论时，可存为 `知识/方法论/需求澄清/资料/会议/2026-10-22.md`，该方法论正文注明会议来源、日期并链接原件。“科学表达”方法论也采用这次会议时，正文链接同一原件，不复制会议文件。原件位置只确定保存责任，不使会议观点自动成为已验证知识；旧实例已有原件仍按原引用读取，迁移须有明确范围。

**示例情境**：对“需求表达为何不等于真实目标”形成新的解释，能够说明依据、反例和适用范围，适合沉淀知识。

**反例情境**：某项目本周采用了新的交付日期，这属于项目事实；仅凭可能被 AI 读取，不构成知识或能力对象的创建理由。

知识内容主要位于 `知识/`，保持普通 Markdown，不注册成能力对象，也不直接套用运行对象的版本与引用契约。名称、摘要和主题等元数据可帮助发现，但不强制每篇补齐一套模板。稳定身份与协作偏好归根 `USER.md`，Agent 协作方式归根 `BOT.md`，跨会话短期续接归根 `MEMORY.md`；公司与业务的当前事实按项目及相关资料保存。三文件不属于知识对象，完整加载、维护和旧画像只读兼容见[根协作约定](../runtime/user-collaboration.md)。

实例组织维护约定的发现入口与导航入口为 `知识/knowledge.md`，新模板默认提供，旧实例缺失也能正常工作；它链接的规则负责保存单元、分类关联、来源、保存合并、复用和纠错，按 [Core 设计方法](../content-design.md)从真实样例逐步确定，不强制统一模型。导航部分对整个知识目录做分层结构化概览：简述各分区承载什么内容，链接到下一级目录或主题综述，便于 Agent 按任务逐层深入。每层只概述当前目录及直接下级主题，不递归枚举全库文件，不展开业务知识正文或具体方法论步骤。子目录可使用 `knowledge.md` 或复用现有主题综述，不强制每个目录新建入口。[模板](../templates/knowledge-index.md)仅供授权后裁剪，不自动创建真实内容。知识模型和目录自由组织，不强制 Y 模型或批量迁移，根导航不替代根协作三文件。常规业务只按本次指定、必要项目事实或采用能力的明确约定读取相关原文；用户明确查阅或整理知识时可沿导航或限定范围检索。调度及异常见[项目与能力路由协作](../runtime/routing.md)。

知识记录、归位与修订由 [knowledge-organize](../../abilities/competencies/knowledge-organize/competency.md) 按实例规则准备专业安排；不同知识单元可以声明不同入口名，例如 cognition.md 或已有主题综述，不要求统一框架。资料读取由承接能力遵循[公共约定](../runtime/materials.md)，按本次指定、项目事实或自身明确约定的范围取得和核对原文；已授权维护由 [asset-maintenance](../../abilities/competencies/asset-maintenance/competency.md)处理。当前由 Agent 使用文件检索、现有 metadata CLI 与宿主编辑工具执行，没有专用知识管理命令或全库语义索引。Core 随包提供[公共组织约定与可选认知框架](../templates/knowledge-index.md)，新实例可直接采用；已有实例只按明确要求合并差异，不自动迁移，其他类型保留各自框架。认知模板定义结构与人发起记录的归位约定，不自动沉淀、代替人采纳认识或转化短期记忆。
