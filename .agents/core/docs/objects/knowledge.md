# 知识 Knowledge

知识承载可以被理解、解释、检验和修订的认知内容。它保存事实、概念、解释、观点与经验认识，以及这些内容的依据和适用条件。

## 解决的问题

人和 AI 都需要知道某个判断为何成立、哪些情境下不成立、证据来自哪里。知识使这种理解可以被反复阅读、讨论、组合和更新，而不依附于某一次任务或某一个搭档。

知识不是能力尚未成形时的临时存放区，也不只是原始材料仓库。它可以长期作为有独立价值的认知存在；原始资料则通过来源关系支持理解与核对。

## 适合承载的内容

- 有适用范围与来源的事实、概念、定义和领域关系。
- 对现象的解释、因果假设、模型与观点。
- 从案例中形成的认识、经验分析、反例与限制。
- 对方法论的解释：为什么有效、依赖什么条件、有哪些争议。
- 支持或反驳上述认识的证据，以及仍待确认的问题。

具体知识不必机械填满这些类别，但应让读者区分事实、他人主张、作者推断和候选认识。形成一篇文档不代表其中判断已经验证。

## 与能力的本质区别

知识保存“理解什么及其依据”；能力规定“承担什么责任、如何处理、怎样协同与执行”。两者都能指导行动，也都可以供 AI 使用，区别在内容的主要责任。

以产品设计为例：

| 内容 | 主要归属 |
| --- | --- |
| 用户常把想到的解决方案表达为需求；这一现象的解释、案例与限制 | 知识 |
| 需求澄清时区分目标与方案，缺少关键情境先追问，结果应满足明确标准 | 基本功 |
| 持续承接用户的产品问题，组织分析并推进到可交付的需求结果 | 搭档 |
| 产品、研发、验证搭档之间的交接与返工机制 | 工作流 |
| 某位用户本次提出什么、团队最终采用什么方案 | 项目 |

“方法论”不是一个自动指向能力目录的标签。讲清一种方法的原理与认识，可以是知识；把它确立为反复采用的专业处理约定，则由基本功持有相应方法与标准。

## 怎样避免重复沉淀

同一材料含有多个层面的内容时，按意义拆分归属，保留关联，不整篇复制：

1. 判断哪些内容是项目中的特定事实，哪些认识可脱离该项目独立理解。
2. 判断哪些内容只是解释或经验，哪些已经形成希望采用的处理方法与标准。
3. 独立有价值的解释保留在知识中；现行专业方法在基本功中维护；两者通过引用连接。
4. 如果整份材料本来就是完整的专业方法，可直接沉淀为基本功，无需先制作知识副本。

反过来，一条认识即使很成熟、很有用，也不必转成基本功。只有需要把它组织为某类专业处理时，才产生这种设计需求。

## 与数据包、项目的边界

知识以认知主题和问题组织理解；数据包以使用情境组织一组资料。知识可以被多个数据包或基本功引用，其主要内容仍在一处维护。让 AI 读取知识，不以先包装数据包为前提。

项目保存具体事情的事实、进展和决定；知识保存可独立讨论的认识。项目案例可以支撑知识，但应保留当时的情境，不把个别结果无条件推广。

新的实践可能支持、限制或推翻原有认识。更新知识时说明证据与影响；如果基本功依赖这条认识，还需检查方法是否应修订，不把知识文件更新等同于所有能力已经同步更新。

## 何时沉淀与存储

**示例情境**：对“需求表达为何不等于真实目标”形成新的解释，能够说明依据、反例和适用范围，适合沉淀知识。

**反例情境**：某项目本周采用了新的交付日期，这属于项目事实；仅凭可能被 AI 读取，不构成知识或能力对象的创建理由。

知识内容主要位于 `知识/`，保持普通 Markdown，不注册成能力对象，也不直接套用运行对象的版本与引用契约。名称、摘要和主题等元数据可帮助发现，但不强制每篇补齐一套模板。`知识/用户画像.md` 是可选配置的短卡入口，由用户维护身份和默认协作约定；ksf-runtime 在首次进入当前 KSF 时读取已配置短卡，未配置时正常运行，系统包不预填私人内容。加载、覆盖与迁移边界见[用户协作约定](../runtime/user-collaboration.md)。

最小发现、来源检查与渐进读取由 [knowledge-route](../../abilities/competencies/knowledge-route/competency.md)持有；已授权维护由 [asset-maintenance](../../abilities/competencies/asset-maintenance/competency.md)处理。当前由 Agent 使用文件检索、现有 metadata CLI 与宿主编辑工具执行，没有专用知识管理命令或全库语义索引。更完整的主题组织与机器契约按实际需求另行设计。
