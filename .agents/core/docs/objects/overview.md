# KSF 对象综述

KSF 用不同对象分别承载认知、具体工作和可复用能力。划分依据是内容承担的责任，以及未来怎样使用它；不能只看名称、篇幅、步骤数量或是否供 AI 阅读。

本目录解释各类对象的内涵、边界和关系，供设计与沉淀时判断承载方式。这些文件是概念说明，不是可调用的对象实例，也不另建一套专业设计方法或运行协议。

## 对象地图

| 类别 | 对象 | 核心问题 | 主要持有内容 |
| --- | --- | --- | --- |
| 运行能力 | [工作流 Workflow](workflow.md) | 多个搭档如何共同完成一类业务？ | 分工、依赖、交接、协调、返工与整体完成条件 |
| 运行能力 | [搭档 Partner](partner.md) | 谁承担这类业务责任，并推动它完成？ | 使命、职责、协作方式、责任—基本功配置 |
| 运行能力 | [基本功 Competency](competency.md) | 一类专业问题或具体操作怎样完成才算做好？ | 处理方法、操作说明、判断标准、正反案例与必要支持 |
| 运行支持 | [数据包 DataPackage](data-package.md) | 当前处理需要哪些成组的信息依据？ | 面向使用情境组织的资料入口、内容说明与来源 |
| 工作资产 | [项目 Project](project.md) | 这件具体的事目前是什么情况？ | 目标、约束、决定、进展、成果和实践记录 |
| 认知资产 | [知识 Knowledge](knowledge.md) | 我知道什么、如何理解、依据是什么？ | 事实、概念、解释、观点、经验分析与证据 |

前四类是当前能力体系中的四类运行对象：工作流、搭档、基本功、数据包。项目、知识在这里作为业务承载概念一起说明；这不表示它们已经具有与运行对象相同的机器类型、入口格式或管理接口。

## 知识与能力的边界

**知识保存理解本身；能力约定如何运用理解履行责任、完成处理或组织协作。** 两者都可以供人和 AI 使用，不能用“给人看”与“给 AI 用”划分目录。

方法论也可能属于知识。例如，对“用户提出的功能可能只是其想到的解决方案”的解释、依据、反例和适用条件，是一种值得保存的认知。把它用于需求澄清，并进一步约定需要问什么、如何区分目标与方案、怎样判断澄清充分，则形成基本功中的专业方法。

一段材料可以同时包含认知、方法和项目事实，但不应整篇复制到三个地方。按各部分的长期用途分别归属，保留来源关系：

- 具有独立理解价值的解释和证据留在知识中。
- 希望反复采用的专业处理规则由基本功持有。
- 只对当前任务成立的事实、决定与成果留在项目中。

完整方法可以直接沉淀为基本功，不要求先制作一份知识副本。知识也不必最终转成能力；它可以长期作为理解、讨论和判断的依据。知识与能力各自可能处于候选或待验证阶段，目录位置不代表成熟程度。

## 责任如何组合

工作流组织多个搭档协作；搭档根据承担的责任选择和组织基本功；基本功统一持有专业方法与具体操作，并按需直接使用脚本、CLI、模板、数据包及其他资料。项目提供本次工作的真实情境，知识提供相关认知与依据。

这说明典型业务关系，不是已经确定的全部引用类型矩阵。共同要求是同一规则有明确的主要维护位置：

| 规则或内容 | 主要归属 |
| --- | --- |
| 需求未澄清时，研发搭档是否可以开始实现 | 工作流中的交接与协同约定 |
| 产品搭档负责把问题推进到可交付的需求定义 | 搭档的责任与协作约定 |
| 怎样区分用户目标、约束和用户提出的方案 | 基本功的专业方法 |
| 怎样调用工具读取记录并生成规定格式的文件 | 基本功的操作说明及所用程序 |
| 本次使用哪些访谈样本、案例和行业资料 | 数据包的资料组织，或项目中的具体选择 |
| 用户实际表达了什么、这次采用哪个方案 | 项目事实与决定 |
| 为什么表达出来的需求可能不同于真实目标 | 知识中的解释与依据 |

其他对象引用这些内容并说明使用情境，避免各自维护一份略有不同的现行规则。能力的运行结果可以产生新的项目证据，进一步修订知识或能力，但不能把一次成功、一次推测自动提升为通用规律。

## 沉淀时怎样选择

先明确希望保留什么、以后怎样复用，再检查已有承载位置。可以复用、完善、组合，也可以暂不创建长期对象。

1. **具体事情的事实与进展**：进入项目。原始文件保留在其源位置，项目提供必要入口，不为归类复制所有原件。
2. **可独立理解的事实、概念、解释与经验认识**：进入知识，说明来源、适用条件和不确定之处。
3. **面向某类处理反复使用的资料集合**：考虑数据包。仅有一份可直接引用的资料时，不必额外包装。
4. **可复用的专业方法或具体执行操作**：进入基本功，明确输入、方法、执行条件和结果标准；已有基本功能承载时优先完善。确定性的细节可交给程序，单步操作不强行独立建对象。
5. **需要有人持续承担的业务责任**：考虑搭档，并配置所需基本功。增加一项专业方法不必增加一个搭档。
6. **多个独立责任需要协同才能完成的业务**：考虑工作流，明确交接与整体完成条件。单个搭档的多步骤处理不因此成为工作流。

这是一组分类判断，不是要求为每项需求建立整套对象。同一输入可以有多个归属，也可以仅更新一个既有对象；重要缺口会改变归属时，先澄清。

设计时的承载判断由 [ksf 对象设计师](../../abilities/partners/ksf-object-designer/partner.md)负责。运行时由 [ability-route](../../abilities/competencies/ability-route/competency.md)选择已有对象，两者不能互相替代。

## 运行时怎样读取

新任务需要选择承接对象时，系统区和用户区的工作流、搭档摘要一起提供给 Agent，按类型区分。先判断是否有适用工作流；没有适用工作流时，再选择搭档。摘要用于发现，候选正文用于确认适用性，不能仅凭摘要命中就开始执行。

选定安排后，再按当前工作需要读取基本功、数据包和具体知识，随后按基本功的实际操作读取模板、脚本或 CLI 说明。引用不等于已经加载，读取不等于已经执行。继续任务优先恢复已有安排，只在目标、范围或关键条件变化时重新判断受影响部分。

[根 AGENTS.md](../../../../AGENTS.md)是特殊入口工作流，连接系统搭档与任务路由。这个入口约定不扩大普通业务工作流的边界，也不要求把每个请求包装成业务工作流。

四类对象的列举、按部分读取、用户写入、完整目录派生、删除和本地引用检查已实现；context capabilities 已组合工作流与搭档的完整有效发现信息。项目基础管理已有 [project CLI](../cli/project.md)，项目筛选、知识读取及资产维护的语义判断由 ksf-runtime 的三项运行基本功承接；尚无专用知识管理命令，见[最小运行闭环](../runtime/minimal-runtime.md)。实际程序接口以 [CLI 说明](../cli/overview.md)为准，能力路由行为以 ability-route 为准。

## 文档与实现的分工

- 本目录说明对象“是什么、负责什么、怎样区分”。各类对象的专业设计方法由对应设计基本功持有。
- 运行对象的公共字段、标识、版本与引用规则统一见[对象元数据规范](../对象元数据规范.md)，不在本目录复制或另定枚举。
- 系统能力位于 `.agents/core/abilities/`，用户能力位于 `能力/`。两者采用一致的对象概念，系统固定入口不能被用户区同名定义覆盖。
- 系统入口、对象设计和最小运行基本功采用公共元数据与精确引用；四类入口及公共对象命令已实现。项目和知识按普通 Markdown 约定读取，完整机器管理规则仍需分别定义。

## 用情境检查边界

| 情境 | 推荐承载 |
| --- | --- |
| 总结关于产品需求的一个新认识及依据 | 知识 |
| 改进知识萃取方法和质量标准 | 基本功 |
| 持续承接用户的知识整理需求 | 搭档 |
| 多个专业搭档协作交付一类功能 | 工作流 |
| 一个搭档处理大量材料 | 沿用搭档与所需基本功，不因工作量创建工作流 |
| 把一组案例组织为不同基本功都能引用的资料 | 数据包，原始来源保持可追溯 |
| 固定执行某种文件转换并检查结果 | 基本功，按需直接调用程序 |
| 记录本次功能开发的约束、取舍和验收结果 | 项目 |
| 现有对象已经能够满足需要 | 复用或完善，无需新建 |

## 能力术语

KSF 的能力总称统一使用 ability，集合目录为 abilities；Workflow、Partner、Competency、DataPackage 是具体能力对象类型。工作流与搭档的选择方法称为能力路由 ability-route，属于 Competency。既有 `context capabilities` CLI 保留为兼容命令名，不因此引入另一类能力对象。任务关系与工作过程由 ksf-runtime 管理。
